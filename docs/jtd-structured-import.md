# JTD構造化インポート

2026-11-10、`jtd-structured-import`。
`0697583`を調べた[デコード監査](jtd-decoding-audit.md)の指摘を修正した。
OpenJTD等の実装は移植せず、公開調査とローカル原本の観察から記述している。
**完全互換ではない。本文の一致と、画面・印刷の一致を区別する。**

## 解析経路

`CFB → DocumentTextブロックディレクトリ → 論理sub-stream → TextV/QLST断片 →
位置付きレコード・書式状態 → 表示行グリッド → ibisOfficeのWordモデル`。

- 本文・書式・パディング・ディレクトリを分離。物理ブロック順を本文順とみなさない。
- 断片を結合してからレコードとUTF-16を処理する。レコード・サロゲートの途中で断片が切れてもよい。
- インラインの5語の終端を検証し、その後の通常本文を再開する。
- 行ヘッダーのTLV全体を読む。`008f`の位置を固定しない。
- 書式イベントの被覆が宣言unit数に一致するか検査する。意味不明の末尾は、そこまでの
  正しく読めた書式と分けて保持する。未対応の書式列は診断付きで保持する。
- `jtd::inspect`は全論理unit、レコード範囲、断片、プロパティ、診断を返す。
  `physical_ranges`で本文unitを元の`DocumentText`内の複数の物理byte範囲へ戻せる。
  JTDへの再保存APIではない。

## Wordモデルへの写像

| JTD | 写像・境界 |
| --- | --- |
| 用紙、余白、書字方向 | 既存`PageSetup`。`1001`が先頭なら縦組みという推測は廃止。`1002`第3群bit0の4-byte先行値は、6文書で観測した-3/-1/0に限定して読み飛ばす。その他の未対応maskでは方向を推測しない。 |
| 既定文字サイズ、字数×行数 | `1006`、`100b`、`100d`から文字サイズとグリッドを設定。DOCXの既定runサイズも保存する。原フォントの選択子と書体の対応は未確定。 |
| 文字書式 | 属性有効bitを確認し、サイズ、太字、斜体、下線、色、白黒反転を`FlowRunStyle`へ。未知のプロパティも解析側には残す。 |
| 段落 | 明示的な左/中央/右揃え、半角桁単位・1/100mm単位のインデント、ぶら下げ、既知の行送りを`ParaFormat`へ。行の途中に来るヘッダーは次の段落状態へ。先頭行の独立した右インデント等は未対応。 |
| ルビ | 読みと本文、本文側の文字書式を保持。明示された読みサイズを使い、それ以外は本文の半分。正確な基線・割付は未対応。 |
| 罫線表示行 | 原区画を削除せず、罫線中心と区画の左右座標からWordグリッド・span・余白を設定。Wordの矩形グリッドを満たす空白は明示的なアダプター上の補完であり、原区画とは区別する。 |
| 区画フラグ | `ff/0`以外の宣言も座標として保持。継続/終端/下方アンカーの意味をWordの論理セル結合へ完全変換したとは主張しない。 |
| 空行 | ゼロ幅の空区画マーカーや文字のない罫線行も表示行として保持する。認識した表示行はWord側で1行に対応し、原本の行ピッチを使う。 |
| 罫線 | 全高、上/下半分、途中/下の水平線、部分線とその端の付加縦線を扱う。線種の属性を読み、既存の`FlowBorder`・`FlowRowLine`を使う。太さ、特殊な線種は一部近似。 |
| 未解読の数値フィールド | 原文と位置・診断を保持し、XMLに不正な制御文字として流し込まない。動的ページ番号等の再計算・表示は未対応。 |

Wordモデルの組版機構を再利用しているが、JTDの表示行をWordの論理表・結合セルへ
同一視していない。読み取り時点で原区画を幅だけで削除する処理は廃止した。
罫線のない/未解読の候補区画に、存在の根拠のない黒い表枠は補わない。
省略された設定には公開調査にある一太郎の既定値（余白30mm、40字×40行等）を使い、
空のWord文書の既定値を流用しない。DOCXでは寸法はtwip、文字サイズは半pointの精度に
丸められるため、JTDの1/100mm値がそのまま往復するとは限らない。

## 検証

- RustのJTD関連テスト32件成功、原本が必要な1件は通常実行ではignore。
- 独立Python診断の合成テスト8件成功。
- ローカルJTD **22件**、計1,290,781本文unitsを実際のRust経路で読み、DOCXへ出力。
  独立診断の本文・ルビ読みと**NFKC・空白除去後の文字順が全件一致**。
  全6,092罫線表示行が、Word側でも同数の表示行として残ることを検査する。
- 対象の新旧対照文書は**4,105文字、4表・130行**。以前の496文字欠落は解消。
  `a5.jtd`は**38,537文字**で一致。旧監査の38,564には、未解読の数値フィールドに
  含まれる27個の制御値が混じっていたため、診断を改めた。これらは本文文字と数えない。
- ブロック順だけ変えた原本コピーと、完全合成した`inline/ordered/reordered`でも照合する。
- 原本は公開アセットに置かず、検証はローカルのみ。私的文書や本文を配布しない。

全体のXLSX integration tests等は不足している別用途のfixtureがあるため、JTD関連に絞った。
上記は文字・レコード・グリッドの検証であり、Word実機・ブラウザー描画との一致ではない。
CUAのブラウザー接続ホストは利用できず、専用プロファイルのヘッドレスChromeでも
Macの表示/GPUエラーで描画を取得できなかった。白い画像を成功として扱わない。

## 完全対応に向けた残り

1. ブラウザーの実描画から、元PDFの線分座標・文字送り・ページ分割との残差を測る。
2. 書体選択子、文字幅・縦横倍率、ルビの配置、未知の段落属性、区画の継続フラグを解読する。
3. 全高罫線とセル境界に写せない線の組合せ、特殊線種・太さを検証する。
   現DOCXは通常のセル罫線を保存するが、`FlowRowLine`の部分線分はまだ出力しない。
4. 複数sheet、見出し/脚注、図形・画像・埋め込み、圧縮/暗号化/旧版など、未対応系統を増やす。
5. 版ごとの一太郎生成probeとPDFを追加し、各機能の受入条件を固定する。

既存の破損した入力や未対応形式を、推測で読めたことにしない。
「完璧」とする条件は、対象版・機能のコーパスと独立した描画期待値で定義する必要がある。
