# JTDの書体・文字送り・罫線の互換性

2026-11-11、`jtd-layout-compatibility`。
[構造化インポート](jtd-structured-import.md)からの追加修正。
公開形式調査と原本の観察を用い、他プロジェクトのパーサー実装は移植していない。
完全な描画互換や、JTDへの書き戻しを実現したものではない。

## 修正

- `FontV.01`をサイズ・件数・文字列長の上限付きで読み、UTF-16BEの書体名、
  weight、italic、charsetを保持する。重複index、切断、未知の末尾は受け入れない。
- `DocumentViewStyles/1006`の2つの明示的フォント参照が、ともに同じ書体・属性へ
  解決する場合だけ既定書体に反映する。ローカル22文書中14文書で「ＭＳ 明朝」を
  適用し、残り8文書では従来の代替書体を維持した。予約値や異なる参照の役割は
  推測しない。インライン文字書式の選択子とFont表のindexを同一視しない。
  書体名はWordモデルの既定値と直接run書式にも保存する。フォントファイルは同梱しない。
- DOCXの既定文字サイズが半pointに丸められる際、文字グリッドの追加間隔を補正する。
  元のモデルは変更せず、DOCXを再読込して再出力しても補正を累積させない。
- 通常本文のルビにも、本文側の太字・色・書体などを適用する。
- セル辺として表現されない全高の罫線、および複数線種からなる下罫線を行内線分として
  保持する。既存のセル辺で被覆される線分は重ねて描かない。画面の行内線分も既存の
  Word罫線描画へ渡し、破線・二重線などの線種を反映する。

## 検証と証拠の範囲

- RustのJTD関連テスト38件成功、原本が必要な1件は通常実行でignore。
  書体のDOCX往復、文字送りの丸め・再出力、本文ルビの属性、罫線の被覆を含む。
- 独立Python診断のテスト10件成功。全幅文字送りのPDF診断では、PDFの抽出結果が
  1文字ずつ別のlineになっていても、同じ基線・書体・サイズの隣接文字を集約する。
- ローカルJTD22文書の本文・ルビ読みは独立診断とNFKC・空白除去後の文字順が一致し、
  6,092罫線表示行を維持。これは文字列と表示行数の検査であり、全書式の一致ではない。
- `03新旧（整備令）`の対応PDFで、全幅文字送りの最頻値±0.25ptに入る3,737組の
  平均は11.211153pt。DOCXの既定サイズとグリッドから計算した送りは、旧版11.071777pt、
  新版11.211914pt。差は約0.1394ptから0.0008ptになった。
  この代表値の一致は、すべての文字・ページ・描画幅の一致を意味しない。
- 専用プロファイルのヘッドレスChromeで、旧公開版と新版を同じローカル原本で開き、
  実際の本文と表ページのスクリーンショットを取得した。新版では既定書体の変更と
  分断された中央罫線の接続を確認した。前回の描画取得不可という制限は、この条件では
  解消した。配信環境と同じHTTPヘッダー、実時間の描画待機が必要だった。
  Word実機での検証、全9ページの画像差分やページ分割の一致は未確認。

ローカル原本・PDF・その画像は公開アセットやGitへ追加しない。
検証コマンドは[構造化インポート](jtd-structured-import.md#検証)と同じ。
`audit-jtd.py`は対応PDFの文字送り統計、`qualify-jtd.py`はDOCX既定書体・送りも出力する。

## 残る差

縦書きの罫線表示行では、JTD側で認識した固定の表示行ピッチをセル内段落の
行送りにも適用する。以前は行の高さだけが固定され、段落の自動行送りで文字が
隣の罫線へはみ出すことがあった。明示された行送りはそのまま使う。これはWord
モデルへの表示上の適応であり、すべてのJTD罫線や書式の完全な再現を意味しない。
手元の `04_250205_1505` の2ページ目では幅を拡大せず重なりを軽減できた。
対応する原本PDFはなく、一太郎本体との描画一致は未検証。

縦書きの傍線は対象文字の右側に描く。行ピッチが文字サイズに近い場合、
従来の傍線と文字の間隔では前の行の文字領域に線がはみ出すため、線の
太さを含む装飾全体が行間に収まるよう、必要な場合だけ対象文字に寄せる。
行間より太い二重線などは、線の太さを変えず文字の右端に寄せる。原本と
対応PDFでの全線種・全ページの一致までは確認していない。

「改正案」「現行」のようなセル内の均等配置が上端寄せになる。文字の縦横倍率、
インラインの書体変更、ルビの詳細配置、区画継続・論理結合、特殊線種・太さなども
完全には解読できていない。フォントの実際の描画は環境の代替フォントに依存する。

画面で使う`FlowRowLine`はDOCXへまだ出力されないため、一部の罫線はWord出力で
失われる。図形・画像、複数sheet、動的フィールド、旧形式・暗号化等の未対応も残る。

## 縦書き罫線行の揃え

縦書きの罫線行に揃え指定がない場合、直前の通常段落の右揃えが表セルへ
引き継がれ、短い文字がセルの下端側に配置されていた。表示アダプターは
各罫線行の開始位置を既定とし、その行自身の `0024` に既知の揃え値がある
場合はそれを維持する。横書きの既存動作と明示的な行揃えは変更しない。

この扱いは観測された罫線行への保守的な補正であり、未解読の一太郎の
揃え設定やすべての文書形式に対する互換性を保証するものではない。
