# 一太郎 JTD 形式の調査メモ

この文書は公開された分析と、手元の文書で確認したバイト列を整理した
**非公式・不完全な作業仕様**である。JustSystemsの仕様書ではない。
書き出しや未知レコードの再構成に使用できる完全な形式定義ではない。

**2026-11-10監査と修復:** 旧実装には本文欠落・ブロック格納の未解読・ヘッダー固定位置への
誤った依存があった。[デコード監査](jtd-decoding-audit.md)と
[構造化インポートの検証結果](jtd-structured-import.md)を参照すること。
以下の罫線座標の部分的な一致は、本文や文書全体を正しく読めたことを意味しない。

## 参照と検証境界

- [OpenJTD RFC 0003/0009](https://github.com/OpenJTD/rjtd/tree/cfb44c9ac53126e00808c49709fb4dade8a4daae/openjtd-spec/rfc): コンテナー、本文、観測されたレコードの分析。
- [EZPZ File JTD の形式調査 §4.3](https://github.com/ezpzfile/ezpzfile-jtd/blob/fe42d44d341f993ae27aa83d3864fba58bb2badc/docs/spec/JTD-FORMAT.md#43-ruled-lines-罫線-new-item-grammar-horizontal-rules): 罫線項目と検証の報告。報告の確度と本プロジェクトでの検証を区別する。
- 個人の実文書と、その一太郎生成PDFはローカルでのみ比較し、配布しない。

公開分析の記述から仕様を整理した後に、ibisOfficeの既存モデルに合わせて
独立に実装する。参照プロジェクトの実装コードを持ち込まない。同一作業者が
資料の収集と実装を行っているため、独立した複数者による正式な
クリーンルーム監査を受けたとは主張しない。

## コンテナーと本文

- JTDはCompound File Binary形式のストリームを持つ。本文候補は
  `DocumentText` で、観測した形式の先頭はASCII `SsmgV.01`。
- 本文中の16ビット単位はビッグエンディアンとして観測される。
- `SsmgV.01`全体を本文とみなしてはならない。ブロックディレクトリからsub-streamを
  再構成し、`TextV.01`または`QLSTV.01`で本文unitと書式領域を分ける。
- 通常の区切りレコードは `001c class length ... length 0000 class 001f`。
  lengthは16ビット単位の数。長さと末尾の反復値を検証してから扱う。
- `0010` は行ヘッダー、`0030` は表示行に含まれる区画候補。
  `0030` の `left`/`right` は同じ行内で順に並ぶ座標候補だが、物理単位は未確定。
- `0010`の内容はTLV列で、`008f`が先頭とは限らない。固定offsetを仕様にしてはならない。
- `000e` は罫線を伴う表示行の区切りとして観測される。論理表の行や
  改ページと同一とは限らない。`0001` のインライン形式は別構造。

## 書字方向

公開調査では `DocumentViewStyles` の `1002` レコード内、複数のビット
マスクに続く第3グループの `0x10` に縦組み設定があるとされる。第3グループの
そのビットより前の項目の長さが既知の場合だけ値を読む。フラグがない場合は
横組みとする。第3群bit0の先行4-byte値は、6文書で観測した-3/-1/0の場合に限って
読み飛ばす。他の未知の項目がある場合は判定を保留し、旧来の紙種による推測には戻さない。

最初のレコードが `1001` かどうかは書字方向そのものではない。手元の横書き
文書1件で `1001` が先頭にあることを確認し、従来の判定だけでは誤った。

## 用紙・余白・行数

公開調査では `DocumentViewStyles` の第1ブロックにある `1001` のビット1・2が
用紙の幅・高さ（単位は1/100mm）、`1002` 第2グループのビット3〜6が上・下・左・右の
余白（同単位）、`100d` のビット1が1ページの行数とされる。既知の先行フィールドを
境界内で読める場合だけ適用し、未対応マスクや不正値は従来の値に戻す。

縦書き時は紙の高さから上下余白を引いた長さを本文・表の進行方向の幅、幅から
左右余白を引いた長さを行数方向とする。横書きはそれぞれ逆である。明示された
行数があるとき、行数方向の長さを行数で割ってWordの行ピッチと表示行の最小高に
写像する。既知の行間指定、字数、文字サイズは構造化インポートで追加した。
書体の選択子、未知の段組・割付等はまだ完全には再現しない。

手元の新旧対照文書では A4、上下16mm・左右20mm、26行を読み、DOCXの
再読み込みでも値が維持されることを確認した。横書きのA4文書と縦書きのA5文書でも
それぞれ用紙・余白・行数を検証した。これだけではページ配置の一致は証明しない。

## `008f` 罫線項目

`0010` ヘッダー内の `008f` 項目に、行全体の幅と複数の線の候補が入る。
固定項目を除いた後は、線の状態と相対距離を持つ4ワードの列で、末尾に
2ワードの短い項目を持つ場合がある。最初の線の中心は起点に1を足した値、
次の中心は前の中心に区間長・距離・2を足した値という報告がある。
最終座標と宣言幅の一致、各範囲、末尾などを確認する。不正・未対応の構造は原unitと
位置を保持するが、正しく罫線として描画できたとは扱わない。

手元の新旧対照文書では、この幅と項目長の一致を128行で確認した。ただし、
他の文書や一太郎の全バージョンに適用できる証明ではない。

| 状態ビット | 公開調査上の意味 | ibisOfficeでの扱い |
| --- | --- | --- |
| `0x10` / `0x20` | 罫線が占める幅の種別 | 中心と区画端との対応を限定的に判定 |
| `0x01`, `0x02` | その表示行の上半分・下半分の縦罫線 | 両方が立つ全高の線はセル左右の罫線へ。半分の線は表示用線分へ |
| `0x04` | 行の途中の横罫線 | 隣接線間と一部の部分線分を表示。DOCXには未出力 |
| `0x08` | 行の下の横罫線 | 隣接する線の中心間を覆う確実な範囲だけセル下罫線へ |

ここでの上下・左右はJTDの横組み座標系の意味で、縦組みページでは
ibisOfficeの既存のページ回転を通る。実際の線の太さ・種類は別のスタイル
情報に入る。構造化インポートでは属性を読んで既存の線種へ写像するが、太さや一部の装飾線は近似する。
一部の途中で終わる線は表示するが、DOCXには出力しない。文字やルビとの重なり、線の優先順位は未対応。
前の行の下罫線が次の行の上端になる場合もあるため、空の表示行を消してはならない。

## 安全性と互換性

- 未知の長さ・終端・配置や座標オーバーフローは罫線として解釈しない。
- 未解読の文書構造を勝手に補完したり、JTDに書き戻したりしない。
- DOCX出力は認識した内容だけの非可逆変換であり、原本の代替ではない。
- 仕様候補は合成データと、権利のあるJTD/PDFの組で検証する。対象文書以外への
  適用範囲、ブラウザーでの表示、Word互換性はそれぞれ別に確認する。
