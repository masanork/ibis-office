# 一太郎 JTD 形式の調査メモ

この文書は公開された分析と、手元の文書で確認したバイト列を整理した
**非公式・不完全な作業仕様**である。JustSystemsの仕様書ではない。
書き出しや未知レコードの再構成に使用できる完全な形式定義ではない。

**2026-11-10監査と修復:** 旧実装には本文欠落・ブロック格納の未解読・ヘッダー固定位置への
誤った依存があった。[デコード監査](jtd-decoding-audit.md)と
[構造化インポートの検証結果](jtd-structured-import.md)を参照すること。
以下の罫線座標の部分的な一致は、本文や文書全体を正しく読めたことを意味しない。

**2026-11-11追記:** ブロック格納・書式イベント・フォント表・既定書体参照の
作業定義を追加した。書体、DOCX文字送り、罫線の修正結果は
[互換性の検証記録](jtd-layout-compatibility.md)を参照。
以下では、元バイト列の構造とWordモデルへの変換方針を区別する。

**2026-11-11追加調査:** JTT/JTTCのコンテナー、埋め込み画像候補、および
罫線行の未解決例を追記した。検体数の少ない観測は一般的な形式規則ではない。

## 参照と検証境界

- [OpenJTD RFC 0003/0009](https://github.com/OpenJTD/rjtd/tree/cfb44c9ac53126e00808c49709fb4dade8a4daae/openjtd-spec/rfc): コンテナー、本文、観測されたレコードの分析。
- ローカルOpenJTD作業ツリー `94e3248` の `openjtd-spec/rfc/0005-jttc-just-compressed-document.md` と `0008-object-stream-candidates.md`: 圧縮と埋め込み候補のドラフト。公開版へのリンクや正式仕様として扱わず、以下のローカル検証やibisOfficeの制約とも区別する。
- [EZPZ File JTD の形式調査 §4.3](https://github.com/ezpzfile/ezpzfile-jtd/blob/fe42d44d341f993ae27aa83d3864fba58bb2badc/docs/spec/JTD-FORMAT.md#43-ruled-lines-罫線-new-item-grammar-horizontal-rules): 罫線項目と検証の報告。報告の確度と本プロジェクトでの検証を区別する。
- 同じ固定リビジョンの[形式調査全体](https://github.com/ezpzfile/ezpzfile-jtd/blob/fe42d44d341f993ae27aa83d3864fba58bb2badc/docs/spec/JTD-FORMAT.md) §2・3・5・6・10: ブロック格納、レコード、文字書式、Font表、文書既定値の公開仮説。
- 個人の実文書と、その一太郎生成PDFはローカルでのみ比較し、配布しない。

公開分析の記述から仕様を整理した後に、ibisOfficeの既存モデルに合わせて
独立に実装する。参照プロジェクトの実装コードを持ち込まない。同一作業者が
資料の収集と実装を行っているため、独立した複数者による正式な
クリーンルーム監査を受けたとは主張しない。

確度の表記は次のように読む。検体の数を、全バージョンの形式保証に読み替えない。

| 区分 | 意味 |
| --- | --- |
| 公開記述＋ローカル整合 | 公開調査に構造の記述があり、手元の入力でも境界や値が整合した |
| ローカル観測 | 自分たちで確認した値・相関。項目の役割の一般化には追加probeが必要 |
| 変換方針 | ibisOffice/Wordモデルに合わせた処理。JTDの仕様そのものではない |
| 未確定 | 元の値・範囲は保持するが、意味や描画を確定していない |

## コンテナーと本文

- JTDはCompound File Binary形式のストリームを持つ。本文候補は
  `DocumentText` で、観測した形式の先頭はASCII `SsmgV.01`。
- 本文中の16ビット単位はビッグエンディアンとして観測される。
- `SsmgV.01`全体を本文とみなしてはならない。ブロックディレクトリからsub-streamを
  再構成し、`TextV.01`または`QLSTV.01`で本文unitと書式領域を分ける。
- 通常の区切りレコードは `001c class length ... length 0000 class 001f`。
  lengthは16ビット単位の数。長さと末尾の反復値を検証してから扱う。
- `0010` は行ヘッダー、`0030` は表示行に含まれる区画候補。
  `0030` の `left`/`right` は同じ行内で順に並ぶ座標候補だが、物理単位は未確定。
- `0010`の内容はTLV列で、`008f`が先頭とは限らない。固定offsetを仕様にしてはならない。
- `000e` は罫線を伴う表示行の区切りとして観測される。論理表の行や
  改ページと同一とは限らない。`0001` のインライン形式は別構造。

### JTTと圧縮JTTC

**ローカル観測。** 無圧縮JTT 3件ではルートの`DocumentText`に通常の
`SsmgV.01`本文があり、独立した抽出との比較で正規化本文・ルビ・罫線行数が一致した。
これらはテンプレート特有の機能や外観の完全な再現を意味しない。

**ローカルOpenJTDドラフト＋ローカル整合。** 手元のJTTC 2件では、外側のCFBの
`/JSCompDocument`を展開すると、内側に`/DocumentText`などを持つ別のCFBが現れる。
`JSCompDocument`は先頭が`26 00`とASCII `JustCompressedDocument`で始まり、
観測例では先頭2 bytesをlittle-endianの長さ38と読んだ位置に`-lh5-`のLHA memberがある。
観測したmemberはlevel 1である。展開結果の全bytesが独立した`bsdtar`展開と2件とも一致した。
これらは観測された部分集合であり、すべてのJTTCや他の圧縮方式の定義ではない。

**ibisOfficeの受理方針。** 宣言位置を使い、LHA level 0/1の`-lh5-`のみを扱う。
展開長・CRC・内側CFBの署名を検査し、外側ファイル64 MiB、圧縮ストリーム32 MiB、
展開結果64 MiBを上限とする。level 0は合成fixtureによる検査であり、実文書での
互換性は未確認。先頭member以外の利用、暗号化、他方式は対応を主張しない。
外側にルート`DocumentText`が存在する場合はそれを優先し、壊れていても別の
圧縮文書へ黙って切り替えない。これらの上限と選択は安全側の実装方針であり、形式上の規則ではない。
2件のJTTCの内側には文字を表示できる本文がなく、画像候補があるため、
アプリは元の文書の再現ではない画像一覧を明示して表示する。

### ストリームの階層

**ローカル観測と受理方針。** 同じ末尾名のストリームが別storageにあっても
ルートの`/DocumentText`と混同しない。`ObjectSheets/DocSheet`などの追加シートや
`EmbedItems`配下の内容は階層付きパスで検出し、変換から省かれる可能性を通知する。
検出数は対応していない全コンテンツの網羅的な数ではない。公開95文書の調査では
追加シート検出0件、埋め込み検出1件だったが、追加シートの不存在を一般化できない。

### 埋め込み画像と配置の候補

**ローカル観測・未確定。** 上記の展開済みJTTC 2件には、
`EmbedItems/Embedding N/\x03EmbeddedPress`がそれぞれ3件と5件あり、先頭に
`METAFILE`を持つ。8件すべてでoffset 48に境界内のWMF候補、offset 110にEMF候補を観測した。
既存のWMF変換器は8件すべてで描画要素を含むSVGを生成したが、外観の正しさは比較していない。
別のEMF変換経路ではSVG出力2件、出力なし6件で、候補の解釈はなお限定的である。

`jtd::inspect_embedded_metafiles`は、このうち`EmbeddedPress`の観測形に限って、
WMFヘッダー・宣言長・レコード境界・終端を検査したバイト列を返す診断APIである。
件数と合計サイズに実装上の上限を設け、不正・未対応の候補を別に数える。
`cargo run -p ibis-pptx --example jtd_embedded -- INPUT`は候補数とサイズのみを出力する。
第2引数に**まだ存在しない**出力ディレクトリを指定すると、候補のWMFと、既存変換器が
描画できた場合は近似SVGを別々に取り出す。既存ディレクトリは変更しない。中断時は
出力が不完全になる場合がある。得られる画像は原本ページではなく、位置や順序も未確定である。
展開済みの実例2件と元JTTC 2件について、抽出したWMF 8件を独立したCFBリーダーで
切り出した結果とバイト単位で照合した。これは描画や配置の検証ではなく、
画像一覧からのDOCX変換や、元の位置に画像を取り込む機能はまだ提供しない。

ローカルOpenJTD分析の`EmbeddingInfo`参照候補とルート`Frame`レコードIDは、
それぞれ3/3、5/5で一致した。これは相関であり、フィールドの確定的意味、
座標の単位、ページとの対応、重なり順、描画可能な位置を証明しない。
実装には対象だけを変更した文書と一太郎生成PDFを使う追加検証が必要である。

**追加の突合（同じローカルJTTC 2件、2026-11-12）。** JTTC内のLHAを別の展開器で
展開し、別のCFBリーダーで`EmbeddingInfo`、`Frame`、各`EmbeddedPress`を読み直した。
OpenJTDで提案されているフィールド位置を使うと、両文書の全8項目
（いずれもクラス名候補`JS.GraphicText.1`）で次の条件が同時に成立した。

- `EmbeddingInfo`の埋め込み番号に対応する`EmbeddedPress`ストリームが存在する。
- `EmbeddingInfo`の枠参照候補に一致する`Frame`レコードIDが一意に存在する。
- 同じ2レコードの幅・高さ候補が両方とも一致する（3/3、5/5）。

この比較では、幅・高さは`EmbeddingInfo`側を32-bit little-endian、`Frame`側を
16-bit big-endianとして読んだ。具体的には、`EmbeddingInfo`の可変長クラス名直後から
参照候補・幅・高さを各4 byte、`Frame`の16-byteヘッダー後の各60-byte行からIDを
offset 6、幅・高さをoffset 36・40の各2 byteで読んだ。値と構造の対応を示す観測であり、画像そのものの表示寸法の
証明ではない。WMFの`META_SETWINDOWEXT`の幅/高さと枠の幅/高さを比較すると、比率の
相対差は1文書の3件で約0.07〜0.64%、もう1文書の5件では1件が約0.71%、残り4件が
約6.4〜6.8%だった。WMF描画変換や配置時の拡縮の影響を調べておらず、原因や最終描画の
一致は判断できない。一方、参照候補を`Frame`の**配列の添字**として扱うと幅・高さの一致は
0/3、3/5にとどまる。また1件は参照候補が0で、ID 0の枠の幅・高さと一致した。
したがって、参照を行番号と決めつけたり、0を一律に不正としたりしない。
OpenJTD側の一部の診断投影ではこれらの仮定を使うため、この2文書の配置の正解として
扱わない。文書は双方とも対応する一太郎出力PDFがなく、対象を移動・拡大した差分もない。
ページ、座標系、アンカー、重なり順の検証は引き続き必要である。

**WMF描画座標の追加観測（同じ2文書）。** 8件すべてのWMF先頭付近には、
`META_SETMAPMODE`値8と`META_SETWINDOWEXT`がそれぞれ1件あり、`META_SETVIEWPORTEXT`は
観測されなかった。値8は[WMF仕様の`MM_ANISOTROPIC`](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-wmf/97b31821-a0db-4113-a210-fffbcedcec4a)で、軸ごとの倍率が異なり得る。
これは取得した範囲の記録の観測であり、WMFの最終描画状態を完全に再生したものではない。
各画像の`SETWINDOWEXT`と`EmbeddingInfo`の幅・高さ候補の比は、1文書では3件とも
横が約0.0283、縦が約0.0281〜0.0284。もう1文書では4件が横約0.0400、縦約0.0426〜0.0428、
1件が横約0.0284、縦約0.0282だった。WMF論理座標をピクセルや物理寸法と断定せず、
差の原因も未確定とする。比の類似や単一の参照関係だけではページ配置を導けない。
`cargo run -p ibis-pptx --example jtd_wmf_frame_probe -- INPUT`は、枠・WMFの候補数と
マッピングレコードを読み取り専用で列挙する。複数候補は選択せず、描画状態の再生や配置は行わない。

**縮小画像と他の枠候補（同じ2文書）。** `EmbedFrame`は8-byte先行部と100-byteずつの
3件・5件に分けられるが、この分割では両文書の計8件がすべて同一のbyte列だった。
ここから画像固有の位置や順序は導けない。別の解釈・版への一般化もできない。

双方の`Thumbnail`には、16-byteの先行部に続き、幅181・高さ256・24-bitの
`BITMAPINFOHEADER`に似た40-byte列がある。先行部の一方の値は40-byteヘッダーと
4-byte境界に揃えた画像行を合わせた139,304 byte、もう一方は16-byte先行部を除いた
保存サイズ（103,577・125,072 byte）に一致した。40-byteヘッダー後の画素候補は、
同一byteが連続しない場合は1 byteのまま、同一byteが2回現れる場合は直後の1 byteを
繰り返し総数として展開すると、双方とも宣言長と一致した。全256行のパディング1 byteは
いずれも0となり、BGR・下端からの走査として表示した結果は、埋め込み画像を含む
自然な縮小画像になった。これはローカル2例の観測であり、他の版への一般化や一太郎での
ピクセル単位の照合を意味しない。埋め込み時点からの変更やページとの対応も未検証で、
現行ページの再構成として扱わない。

`cargo run -p ibis-pptx --example jtd_thumbnail_info -- INPUT`はヘッダー候補を検査する。
第2引数に**まだ存在しない**BMPファイルを指定すると、この限定形を長さ・連長を検査して
展開する。既存ファイルは上書きしない。書き込み中の中断では出力が不完全になることがある。
画像は埋め込みスナップショット候補であり、元の画像の位置や順序を確定するものではない。

### `SsmgV.01`のブロック格納

**公開記述＋ローカル整合。** 以下の整数はビッグエンディアン。
`byte`と16-bitの本文`unit`を混同しない。

| byte offset | 内容 |
| --- | --- |
| 0 | ASCII `SsmgV.01`（8 bytes） |
| 8 | `u32 sub_count` |
| 12 | `u32 block_size`。ローカル入力では256 bytes |
| 16 | `u32 block_count` |
| 20 | `block_count * block_size` bytesのブロック領域 |
| 直後 | `sub_count`個のディレクトリ項目、最後に`u32 0` |

ディレクトリ項目は、
`u32 index, u32 reserved, u32 byte_length, u32 n, u32 repeated_n, u32 block_id[n]`。
現在扱う形では`reserved = 0`、`n = repeated_n`。
block idは0起算で、格納位置は`20 + block_id * block_size`。
**列挙された順序**でブロックを連結し、`byte_length`で末尾を切る。
未使用ブロック、ブロック末尾のパディング、ディレクトリは本文に含めない。
重複index、ブロック参照の重複・範囲外、容量を超える長さ、未知の末尾を
現decoderは不正または未対応として拒否する。これは受理する部分集合の条件でもある。

sub-stream 0の2形式は次のとおり。

```text
TextV.01: magic[8], u32 unit_count, u16 text[unit_count], style_events[]
QLSTV.01: magic[8], u32 piece_count,
          (u32 unit_count, u32 sub_index)[piece_count], optional_u32_trailer
```

`TextV.01`は本文開始byte offset 12。`QLSTV.01`の各pieceは、参照sub-streamの
先頭から宣言unit数の本文、その直後にpieceの書式イベントがある。
piece一覧の順に本文unitsを連結してからレコードとUTF-16を解析する。
piece境界はレコード境界・サロゲート境界とは限らない。
書式のunit位置にも、piece以前の累計unit数を足す必要がある。

**ローカル観測:** piece-listの末尾に公開記述より4 bytes多い例がある。
4-pieceの例で値0、40-pieceの例で39を観測したが、意味は未確定。
現decoderは末尾なし/4 bytesの形を受理し、その値を保持する。
単なる未使用パディングや「piece数−1」と断定しない。

`jtd::inspect`は論理unit範囲、piece、物理ブロック参照を返す。
`physical_ranges`はその範囲を**CFB内のDocumentTextストリーム相対byte位置**へ戻す。
CFBファイル先頭からの絶対offsetではなく、複数の物理範囲になることもある。

### レコードの長さとインライン終端

**公開記述＋ローカル整合。** 通常レコードの`length`はpayload長でなく、
先頭`001c`から末尾`001f`までを含むunit数。

```text
001c class length payload[] length 0000 class 001f
```

class `0001`の観測されたインライン形は別扱いにする。

```text
001c 0001 0007 0000 selector_a selector_b 001d
inline_units[]
001e 0005 0000 0001 001f
```

`0007`を通常レコード全長とみなさない。5-unitの終端をすべて検証し、
終端の次から通常の本文走査を再開する。次の`001c`まで読み飛ばすと平文が欠落する。
行ヘッダーclass `0010`のpayloadは先頭`0000`、
`u16 tag, u16 count, u16 values[count]`の列、終端`ffff 0000`。
この`count`もbyte数ではなくunit数。`008f`を探す際はTLVを順に読む。

**ローカル観測と変換方針:** inlineの`(selector_a, selector_b) = (0,1)/(0,3)`の
直後に`(1,0082)`がある形を、本文とルビ読みへ対応させる。
全selectorを解読したわけではない。制御値を含む数値フィールドは
一般のUTF-16文字列として出力せず、位置と原unitを診断側に保持する。
本文とルビ読みの検査は別に行い、未知の動的フィールドを本文文字数へ加えない。

### 本文unitに対応する文字書式イベント

**公開記述＋ローカル整合。** 本文の直後の書式領域はbyte単位の命令列。
数値やプロパティ値の複数byte整数はビッグエンディアンとして読む。

```text
00 <u32 n>                         現在の書式が次のn unitsを覆う
fe (<u8 id> <u8 byte_length> <value[]>)* ff 00
                                   書式状態を変更し、1 unitを覆う
ff                                 末尾の終了候補
```

書式状態は次の命令へ継続する。通常runのunit数と変更命令の個数の合計が、
pieceの本文unit数と一致することを検査する。`ff`だけを探して終了としない。
最終runの直後にsub-streamが尽きる形も観測した。
現decoderはpieceごとに解析・被覆検査し、末尾のゼロ長runや単独`ff`を許すが、
被覆後の未知の末尾は診断と原byte列を残す。ローカル22文書中1文書の1pieceには
未対応の書式末尾が残っている。本文が読めることと全書式が読めることは別である。

| property | 現在使う解釈 | 境界 |
| --- | --- | --- |
| 2（2 bytes） | 文字サイズ、1/100mm | 0は既定。実装では有効範囲も検査する |
| 13（2 bytes） | 下線の種類。1=単線、2=太線 | 20の下線有効bitも必要 |
| 15（4 bytes） | `00BBGGRR`の文字色、`ffffffff`は自動 | 自動は既定色を維持 |
| 20（4 bytes） | 属性有効・太字・斜体・下線・反転のbit群 | `80000000`がない場合、他の属性値だけで有効にしない |
| 3 / 8 | 書体選択子の候補 | `/Font`のindexとの対応は未確定 |
| 4 / 5、その他 | 縦横倍率等の候補・未知値 | 数値を保持するが、倍率や基線移動等への完全写像はしない |

20のbits 26–27は太字、28–29は斜体の候補で、それぞれ1/2でon、0/3でoff。
`00000010`は下線有効、`00000008`は白黒反転として扱う。
Font表のweightだけで、インライン書式の太字を判定してはいけない。

## 書字方向

公開調査では `DocumentViewStyles` の `1002` レコード内、複数のビット
マスクに続く第3グループの `0x10` に縦組み設定があるとされる。第3グループの
そのビットより前の項目の長さが既知の場合だけ値を読む。フラグがない場合は
横組みとする。第3群bit0の先行4-byte値は、6文書で観測した-3/-1/0の場合に限って
読み飛ばす。他の未知の項目がある場合は判定を保留し、旧来の紙種による推測には戻さない。

最初のレコードが `1001` かどうかは書字方向そのものではない。手元の横書き
文書1件で `1001` が先頭にあることを確認し、従来の判定だけでは誤った。

## 用紙・余白・行数

公開調査では `DocumentViewStyles` の第1ブロックにある `1001` のビット1・2が
用紙の幅・高さ（単位は1/100mm）、`1002` 第2グループのビット3〜6が上・下・左・右の
余白（同単位）、`100d` のビット1が1ページの行数とされる。既知の先行フィールドを
境界内で読める場合だけ適用し、未対応マスクや不正値は従来の値に戻す。

縦書き時は紙の高さから上下余白を引いた長さを本文・表の進行方向の幅、幅から
左右余白を引いた長さを行数方向とする。横書きはそれぞれ逆である。明示された
行数があるとき、行数方向の長さを行数で割ってWordの行ピッチと表示行の最小高に
写像する。既知の行間指定、字数、文字サイズは構造化インポートで追加した。
書体の選択子、未知の段組・割付等はまだ完全には再現しない。

手元の新旧対照文書では A4、上下16mm・左右20mm、26行を読み、DOCXの
再読み込みでも値が維持されることを確認した。横書きのA4文書と縦書きのA5文書でも
それぞれ用紙・余白・行数を検証した。これだけではページ配置の一致は証明しない。

### `DocumentViewStyles`の外枠と文字グリッド

**公開記述＋ローカル整合。** 現在読んでいる先頭ブロックは、
`00 01 00 02 10 00`、`u32 byte_length`、その長さのレコード列。
レコードは`u16 tag, u16 byte_length, value[]`。本文ヘッダーのTLVとは長さの単位が違う。
後続ブロックまで既知の意味を持つとみなさない。各値のmaskは変更された設定だけを
格納し、立っているbitの項目が昇順に続くという公開仮説に従う。

- `1006`の最初のmaskのbit0: 既定文字サイズ`u32`、1/100mm。
- `100b`の最初のmaskのbit7: 1行の半角桁数`u16`。80なら全角40字。
  前にあるbit0は1 byte、bit1は2 bytes、bit2/4/6は各1 byte。
  現実装は既知maskの範囲でbit7の位置を求める。未知項目を固定offsetで飛ばさない。
- 全角送りの候補値は`本文進行方向の長さ * 2 / 半角桁数`。
  `本文進行方向の長さ`は、横組みなら用紙幅−左右余白、縦組みなら用紙高−上下余白。
  文字サイズと送りは別の量であり、字間は送りから文字サイズを引いた値となる。

**変換方針:** ibisOffice内部は1pt=12,700 EMU、文字サイズは1/100pt、
DOCXの既定文字サイズは半point単位、`docGrid.charSpace`は1/4096pt単位。
文字サイズが丸められた場合は、その差をグリッドの追加間隔へ移して送りを維持する。
これは出力形式への適応であり、JTDにその補正フィールドがあるという意味ではない。

## `FontV.01`と既定書体

### Fontストリームの構造

**公開記述＋ローカル整合。** `/Font`の形は次のとおり。文字列はUTF-16BEで、
ゼロunitを終端とする。indexが連番であるとは仮定しない。

```text
"FontV.01" u16 count
各font:
  u16 index
  byte fixed[28]
  u16 face_name[] 0000
  byte unknown[12]
  u16 style_name[] 0000
```

28-byte固定部の先頭から+16にweight候補`u32`、+20にitalic候補`u8`、
+23にcharset候補`u8`。LOGFONT類似の並びだが、他の全項目の意味や単位は確定しない。
現在のparserはweightを0〜1000、italicを0/1の部分集合に限定し、
1MiB・1024書体・文字列の終端を含む1024 unitsを上限としている。
これらの上限は防御的な実装方針であり、JTD一般の形式上限ではない。
ローカル22文書でFont表の末尾まで構造が整合した。未知の12 bytesは解釈しない。

### `1006`の参照候補

**ローカル観測。** `DocumentViewStyles/1006`の最初のmaskで、
bit1・bit2の項目はそれぞれ`u16`のFont表参照候補。
bit0の文字サイズがある場合はその4 bytesの後、ない場合はmaskの直後に来る。
2参照の別々の役割（和文/欧文など）は未確定である。

**変換方針:** 両bitが明示され、両参照が存在し、書体名・weight・italic・
style名・charsetが一致するときだけ、その共通書体を文書既定値とする。
ローカル22文書のうち14文書で「ＭＳ 明朝」が解決し、残り8文書は従来の代替書体を使う。
予約値`fffe`を含む例では、もう片方が有効でも意味を補って適用しない。
この安全側の一致条件は、2参照が常に同じでなければならないという形式規則ではない。

インラインproperty 3/8をこの同じindex空間として扱う証拠はない。
書体名が解決してもフォントファイルが含まれるわけではなく、実際の字形は表示環境に依存する。

## `008f` 罫線項目

`0010` ヘッダー内の `008f` 項目に、行全体の幅と複数の線の候補が入る。
固定項目を除いた後は、線の状態と相対距離を持つ4ワードの列で、末尾に
2ワードの短い項目を持つ場合がある。最初の線の中心は起点に1を足した値、
次の中心は前の中心に区間長・距離・2を足した値という報告がある。
最終座標と宣言幅の一致、各範囲、末尾などを確認する。不正・未対応の構造は原unitと
位置を保持するが、正しく罫線として描画できたとは扱わない。

手元の新旧対照文書では、この幅と項目長の一致を全130行で確認した。
旧実装が数えた128行は`008f`の前に別TLVがある2行を落としていた。
ローカル22文書では6,092項目で幅が整合した。ただし、
他の文書や一太郎の全バージョンに適用できる証明ではない。

| 状態ビット | 公開調査上の意味 | ibisOfficeでの扱い |
| --- | --- | --- |
| `0x10` / `0x20` | 罫線が占める幅の種別 | 中心と区画端との対応を限定的に判定 |
| `0x01`, `0x02` | その表示行の上半分・下半分の縦罫線 | 両方が立つ全高の線はセル左右の罫線へ。半分の線は表示用線分へ |
| `0x04` | 行の途中の横罫線 | 隣接線間と一部の部分線分を表示。DOCXには未出力 |
| `0x08` | 行の下の横罫線 | 隣接する線の中心間を覆う確実な範囲だけセル下罫線へ |

ここでの上下・左右はJTDの横組み座標系の意味で、縦組みページでは
ibisOfficeの既存のページ回転を通る。実際の線の太さ・種類は別のスタイル
情報に入る。構造化インポートでは属性を読んで既存の線種へ写像するが、太さや一部の装飾線は近似する。
一部の途中で終わる線は表示するが、DOCXには出力しない。文字やルビとの重なり、線の優先順位は未対応。
前の行の下罫線が次の行の上端になる場合もあるため、空の表示行を消してはならない。

**ローカル観測と変換方針:** 罫線座標とclass `0030`の区画座標は別に保持する。
全高の線でも区画の内部にあれば、Wordのセル左右の辺だけでは表せない。
また、複数の線種に分かれる下罫線を単一のセル下辺へ縮約すると線が消える。
現在は実際のセル辺で覆われる線と、追加の行内線分にする線を分け、二重描画を避ける。
これは表示アダプターの都合であり、JTD内でその線が別種のレコードになるという意味ではない。

`0030`の区画宣言は観測形`0000 left right flags 0000`のまま保持し、
`flags`が`00ff`または`0000`でないことを理由に区画や本文を削除しない。
幅の狭い空区画、罫線だけの行、継続フラグを、不要なデータと同一視しない。
Wordの矩形グリッドを満たす空の補完セルと原区画は区別する。
セル結合・継続・均等配置を完全に解読したわけではない。

**未確定:** 公開95文書の独立比較で、94件は本文・ルビ・罫線行数が一致した。
残り1件は本文とルビが一致した一方、罫線ヘッダー48件に対し出力行は47行だった。
48件目のヘッダーには改ページ前に`000e`終端がなく、既存実装でも同じ差がある。
この観測だけでは欠落行か別の制御構造かを判断できないため、行を推測して補わない。

## 安全性と互換性

- 未知の長さ・終端・配置や座標オーバーフローは罫線として解釈しない。
- 未解読の文書構造を勝手に補完したり、JTDに書き戻したりしない。
- DOCX出力は認識した内容だけの非可逆変換であり、原本の代替ではない。
- 仕様候補は合成データと、権利のあるJTD/PDFの組で検証する。対象文書以外への
  適用範囲、ブラウザーでの表示、Word互換性はそれぞれ別に確認する。
