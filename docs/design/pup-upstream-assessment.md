# 行政事務標準文字・後方互換 PUP の上流向け調査（作業中）

## 検討中の方針（2026-11-16、従来の試作を見直す）

ユーザーの方針: 後方互換 PUP や住基ネット統一文字コードは入力時の互換形式として扱い、対応が確実な場合は Unicode / 登録済み IVS や Unicode の結合文字列へ変換する。新形式への変換ではこれらの旧符号を出力せず、PDF の検索・コピー用文字列も変換先を使う。行政事務標準文字の暫定利用 PUP も、標準化と正式な対応関係が確認されたものから移行する。字形を推測して基底字に丸めたり、異体字照合のクラスタを変換根拠に使ったりしない。

### 元ファイルと同形式で上書きするとき

レセプト等のレガシー連携を守るため、同じ CSV 等の元ファイルを上書きする場合は、読み込んだ元の文字コードを維持する。Shift_JIS と CP932 等は同一視せず、判別または利用者が指定した具体的な符号化方式を記録する。BOM、区切り、改行等も維持すべき対象として検証し、出力時に情報落ちする文字は変換先と場所を示して上書き前に失敗させる。黙った置換や数値文字参照への変換はしない。異なるバイト列が同じ文字に復号されることもあるため、符号化方式の維持だけを元バイト列の完全な再現とは呼ばない。元の字形識別に特定の外字割当が必要な場合は、その入出力体系と対応表を別途明示し、Unicode へ変換した結果を無条件に逆変換しない。

PDF / OOXML への変換は別経路であり、対応が確かな標準 Unicode / IVS を出力する。同形式・同一ファイルの上書きと、新規保存・異形式変換は混同しない。自動判定だけで文字コードを一意に決められないデータでは明示的な選択を可能にする。

現状調査: `crates/ibis-pptx/src/csv.rs` の `decode` は文字列だけを返し、元の文字コードを返さない。通常の CSV 保存は `crates/ibis-office-xlsx/src/event_hooks.rs` から UTF-8 BOM の `sheet_to_csv` を呼ぶ。明示的な Shift_JIS 書出しも、`encoding_rs::SHIFT_JIS.encode` のエラー有無を無視している。上書き時の保持・厳密なエラー処理はいずれも未実装である。

「読込のみ」と既存 XLSX 等の扱いの境界は未実装。既存ファイルを開いただけで上書きせず、変換処理の対象文書・文字体系を明示する。変換の有無と件数・未変換・曖昧な対応を示し、新規保存先を設ける設計を検討する。変換元のまま保存することを標準方針とするのではなく、変換できないデータを黙って削除・別の字形に置換しないための保護である。名前・住所、式・参照、共有文字列、図形テキスト、注釈、隠しシート等を含めた対象範囲と、文字長変更に伴う位置・書式の維持を明確にする。住基コードが識別子として記載された単なる `J+....` 文字列と、コード体系であると判明した入力を区別する。

U+10022A → U+00E6 U+0300、U+101000 → U+3404 U+E0101 は、手元の表に基づく変換例である。通常の U+00E6 U+0300 が PDF から U+00E6 U+0060 と抽出される現象は、望ましい標準化ではなく別文字への誤変換であり、元の標準文字列を保持する修正が必要。IVS の字形・検索・抽出結果を確認し、フォントに字形がないときは別の字形を正解として扱わない。

対応表は版・出典・配布条件を固定し、Unicode/IVD の登録バージョンを記録する。将来の暫定 PUP→標準表現の対応は正式な根拠が得られた時点で更新する。Unicode にまだ対応がない場合は、未変換として利用者に示し、文書を壊さず適切に扱う。自治体標準準拠システムの交換要件では、後方互換 PUP と標準化までの暫定 PUP の扱いは異なる。[デジタル庁の検討会資料](https://www.digital.go.jp/assets/contents/node/basic_page/field_ref_resources/f9a1564c-85d0-46ee-8bfb-4c57e5005c8b/f4d9c775/20240130_meeting_local-governments-character-operation_outline_01.pdf)及び[有識者会議資料](https://www.digital.go.jp/assets/contents/node/basic_page/field_ref_resources/bff3da07-c47d-4204-93f6-2dca5d9de7e4/7c578f8b/20250411_meeting_local-governments-character-specification-revise-experts-meeting_01.pdf)を参照。

以下は以前の、文字コードを変えずに描画する試作の証拠であり、上記の標準化方針を実装したものではない。

## 符号と字形の対応

手元の `gjs/data/sources/custom/pup_to_ivs.csv`（SHA-256 `0dd259bc4fc21501f8984bdf267560f7612e21da387221bbf9f5b12e023b0d85`）10,207 行について、別に保存した `mjq/data/mj-pup.csv`（`016fabd626be1b4294d7c9efceaecbe1c056116533392b1dac0dcf8814c84f38`）の PUP→MJ 番号と `mjq/data/mji.00602.csv`（`d95af7984ce026b9730638c8beda086c9428e964c6cdf2d8a9c9371d2aef5088`）の MJ→Moji_Joho IVS を連結して比較し、先頭の基底字＋セレクタは 10,207 件すべて一致した。`scripts/audit-local-pup-mapping.py` で再現できる。

ただし二つの変換表の出典は無関係とは確認できていないため、これは整合性確認であって独立した正解データによる検証ではない。gjs の導入コミット `5161eba` は mjq/jkc からの取得を記述。mjq の `53e239e85` と抽出スクリプトは SQLite の `pup_ivs`・`dictionary` から導出したことを示す。`mjq/src/import_pup.py` は MJ 番号と PUP の CSV を読み込むが、元資料の具体的な版・加工履歴・再配布条件は未確定。第三者データの条件は調製者クレジットだけでは解消しない。

元 CSV の各 IVS 欄は基底字＋セレクタ＋別のセレクタの 3 符号で、先頭 2 符号だけが上記参照データと一致する。後ろのセレクタを選んではならない。IPAmj 006.01 から生成したローカル alias の 10,207 グリフは、選択した IVS の輪郭と一致したが、それは参照データの正当性を単独で保証しない。フォントとデータの配布条件は別に確認する。

後方互換 PUP には、MJ/IVS 用の 10,207 件以外に結合文字の対応もある。手元の `mjq/data/pup-combind.csv`（SHA-256 `d2d6b3d196f91ba4f1290026e768b7ef587692ac09679c22f592d4b26f1edceb`）には 202 件あり、例 U+10022A は U+00E6 + U+0300。手元の追加明朝には 202 件とも含まれない。CSV の来歴と内容の妥当性は別途要確認。`U+101000..U+104295` の固定範囲だけで後方互換 PUP を網羅したとは言えない。

ローカル試作では HarfBuzz 15.1.0 と IPAmj 006.01 でこれら 202 文字列を組み、各々が位置・幅の補正なしの単一字形になることを確認して、10,207 件の漢字と同じローカル alias フォントへ追加した。複数字形、欠落字形、位置や幅に補正がある結果は拒否する。`scripts/verify-local-pup-alias.py` により 202 件の輪郭と文字幅も確認。異なるフォント・shaper・版で必ず同じ条件となる保証はない。

合成 XLSX を用いた macOS のシート表示・セル編集・保存・PDF 出力では、ラテン文字、かな、変体仮名、声調記号の例について、PUP と元の結合文字列を並べて描画し、PUP の保存値と PDF 抽出値を確認した。ただし PDF の通常の結合文字列は、見た目が正しくても元のコード列を抽出できない場合があった（U+00E6 U+0300 が U+00E6 U+0060 となる例）。PDF の字形から文字を逆引きする既存経路の問題であり、この試作は通常の結合文字列・IVS の PDF テキスト保持を保証しない。

## 上流向けに解くべきこと

1. 管理者・利用者が明示的に指定した文字体系だけに適用し、一般の PUA や文書指定書体の外字を勝手に置き換えない。字形がない場合の誤表示・欠落を利用者に分かる形にする。
2. 名前で特殊扱いしたローカル GPUI パッチはそのまま提出しない。upstream `gpui-pre-macos` は英字 `m` のないフォントを拒否する。テキスト計測の `em_width` / `em_advance` も `m` を要求しており、例外をグローバルに許すだけでは呼び出し側の安全性を保証しない。対象文字用のフォールバック専用 face と計測の前提を設計・検証する。
3. 互換 PUP のレンダリング時の IVS 解決は元の文字列と編集位置を保つ。正規化変換・コピー・PDF テキスト・外部交換の扱いは別に定め、無言で基底字に落とさない。前述の結合文字も対象範囲を確認する。
4. 通常文字との混在、書体・太字・斜体、字形欠落、ユーザー定義 PUA、改行・選択・カーソル・IME・コピー・保存と再読込、印刷・PDF の埋め込みと抽出を確認。macOS / Windows / Linux / Web それぞれの証拠を明示する。
5. 行政明朝の[提供元](https://www.digital.go.jp/policies/local_governments/character-specification)、[IPAmj の提供元と利用条件](https://moji.or.jp/mojikiban/font/)、対応表それぞれの具体的な版・出典・配布条件を固定。外部フォントの派生物と PDF への埋め込みも確認する。

## #158 へのコメント下書き（未投稿）

XLSX のシート表示、編集、PDF 出力についても、行政事務標準文字と後方互換 PUP を検証対象に含めたいです。

ローカルの macOS 試作では、追加明朝の文字と後方互換 PUP を含む合成シートで、元のセルの符号を保持しつつ表示・編集し、PDF にフォントを埋め込めました。後方互換 PUP は IPAmj の Moji_Joho IVS に対応する字形を参照しています。この結果は限定的な試作で、他 OS、Web、印刷、対応字形全体は未確認です。

対象の文字体系を明示し、文書固有の外字を誤って置き換えないこと、対応字形がない場合の扱い、書体指定、編集時の文字位置、保存・PDF とテキスト抽出を確認したいです。後方互換 PUP には結合文字の対応もあるため、漢字 IVS だけを全体の対応としないようにします。対応表とフォントの版・来歴・配布条件も調査中です。

なお、ローカルでは macOS 描画基盤の英字 `m` を持たないフォントの扱いを変更していますが、既存の幅計測との整合性を確認できていないため、現在の例外処理を上流に採用できるとは考えていません。
