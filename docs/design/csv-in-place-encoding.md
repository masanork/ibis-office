# CSV / TSV の文字コード保持（試作）

元の CSV / TSV に上書きするときは、読み込み時に判定した UTF-8（BOM の有無）、UTF-16 LE/BE（BOM 付き）、CP932、区切り文字、行区切り（CRLF / LF / CR）と末尾の改行の有無を維持する。行区切りの混在、閉じられていない引用、または引用セル内の CR は、現在の読込処理が再現できないため上書きを拒否する。新しいパスへの CSV 出力は従来どおり UTF-8 BOM とし、その後の上書きでは新しい形式を使う。PDF / OOXML 出力はこの文字コードを使わない。

入力が ASCII のみ、または UTF-8 と CP932 の双方として有効なら、バイト列だけでは区別できない。ネイティブ版では開く際に UTF-8 または CP932 の選択を求め、選択した文字コードで読み直す。選択中や読み直し中にファイルのサイズ・更新時刻が変われば中止する。選択処理を通らない経路では曖昧な形式を記録し、ASCII 以外を含む同一ファイルの上書きを拒否する。選択肢の Shift_JIS は CP932 で、厳密な Shift_JIS や独自外字の選択は未対応。

CP932 に表現できない文字があるときは出力せず、数値文字参照などの代替も書かない。同一ファイルとしての判定は同じパス・シンボリックリンク・ハードリンクを考慮する。通常保存、同じファイルへのコピー保存、CSV / TSV 書き出しで同じ判定を使う。CSV を別の書式へ移す場合は、その書式の既存出力処理を使う。

macOS の合成データで、CP932 の同一ファイルへの編集・保存、表現できない文字がある場合の無変更、別パスへの UTF-8 出力とその再保存をシナリオで確認した。既存の無関係なテストコードにある PDF 分岐漏れ 10 件をテスト時のみ補い、検証後に元に戻したため、現状のツリーからシナリオ全体をそのままコンパイルできたという意味ではない。

ネイティブ画面でも、同じ曖昧なバイト列を UTF-8 と CP932 のそれぞれで開き、異なる文字として表示・編集・同一ファイルへ保存できることを確認した。選択中にサイズと更新時刻が変わった場合は、読み込みを中止することも確認した。この検知は内容のハッシュ比較ではない。

未完了: Windows / Linux / Web の検証、厳密な Shift_JIS、レガシー外字の対応表と編集・同一形式書き戻し、Unicode / IVS への変換、PDF のテキスト抽出。混在改行や引用セル内の CR も保存できるようにすること、引用方式や未編集部分のバイト単位の一致は今後の課題。CP932 でも同じ Unicode が複数のバイト列を持ちうるため、符号化方式の維持とバイト完全一致は別の条件である。

特に現在の試作はシートから CSV を再構築するため、未編集でも `00123,1.20` が `123,1.2` に変わり、行ごとのフィールド数や末尾の空フィールドも変化しうることを合成データで確認した。レセプト等の同一形式上書きには適さない。元のフィールド表現とレコード構造を保持し、編集分のみを安全に反映する仕組みと、その検証が必要である。
