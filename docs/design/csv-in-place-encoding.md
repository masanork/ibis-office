# CSV / TSV の文字コード保持（試作）

元の CSV / TSV に上書きするときは、読み込み時に判定した UTF-8（BOM の有無）、UTF-16 LE/BE（BOM 付き）、CP932 と区切り文字を維持する。新しいパスへの CSV 出力は従来どおり UTF-8 BOM とし、その後の上書きでは新しい形式を使う。PDF / OOXML 出力はこの文字コードを使わない。

入力が ASCII のみ、または UTF-8 と CP932 の双方として有効なら、バイト列だけでは区別できない。この試作は UTF-8 として読みつつ曖昧な入力だと記録し、ASCII 以外を含む同一ファイルの上書きを拒否する。明示的なエンコーディング選択は未実装。入力を正しく読めたと断定できないため、利用者が文字コードを指定して再読込できる UI が必要。

CP932 に表現できない文字があるときは出力せず、数値文字参照などの代替も書かない。同一ファイルとしての判定は同じパス・シンボリックリンク・ハードリンクを考慮する。通常保存、同じファイルへのコピー保存、CSV / TSV 書き出しで同じ判定を使う。CSV を別の書式へ移す場合は、その書式の既存出力処理を使う。

macOS の合成データで、CP932 の同一ファイルへの編集・保存、表現できない文字がある場合の無変更、別パスへの UTF-8 出力とその再保存をシナリオで確認した。既存の無関係なテストコードにある PDF 分岐漏れ 10 件をテスト時のみ補い、検証後に元に戻したため、現状のツリーからシナリオ全体をそのままコンパイルできたという意味ではない。

未完了: 曖昧な符号化方式の明示選択、Windows / Linux / Web の検証、レガシー外字の対応表と編集・同一形式書き戻し、Unicode / IVS への変換、PDF のテキスト抽出。CSV の記録区切りは現在 CRLF として書き出され、行末・引用方式や未編集部分のバイト単位の一致は保証しない。CP932 でも同じ Unicode が複数のバイト列を持ちうるため、符号化方式の維持とバイト完全一致は別の条件である。
