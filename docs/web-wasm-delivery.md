# Web Wasm delivery

The web build produces a manifest with SHA-256 and 20 MiB chunks. It also builds a Brotli representation of the same module using the Node.js Brotli encoder at quality 5. When that representation is at most 25 MiB, the manifest names the compressed asset by its own hash. If it is too large, the build leaves the single representation out and the app uses the chunks.

On the Cloudflare Worker, `/pkg/br/<compressed-sha256>.wasm` streams the compressed asset with `Content-Encoding: br` and `Content-Type: application/wasm`. The browser automatically decodes it; the loader checks its decoded size and the manifest's whole-module SHA-256 before starting the app. A client that does not accept Brotli gets 406. Missing, unavailable, corrupt, truncated, oversized, or undecodable single responses fall back to the original chunks, which are each verified and then verified again after reconstruction. Hosting without the Worker also falls back to chunks when the single route is absent.

The Brotli URL is content-addressed and uses `Vary: Accept-Encoding` and an immutable cache policy. The Worker streams compressed bytes using manual encoding rather than buffering them. This preserves the original font, sample, and authentication routes. Browser startup progress counts decoded bytes and resets if it switches to chunks.

To verify a deployment, compare the public manifest to the build output, check the Brotli response's headers and decoded SHA-256 on both domains, test a browser launch and document, and force the single route to fail to confirm the split path. Check a request with `Accept-Encoding: gzip` returns 406 without downloading the Brotli asset. The usual Worker dry-run verifies packaging, not remote routing or browser behavior.

When deploying over an older split build, retain its content-addressed chunk files in the new asset directory long enough for already-open tabs and cached manifests, and verify that each old URL remains reachable on both domains after deploying. `scripts/split-web-wasm.py` removes stale chunks from its build output, so copy verified previous chunks into the deployment directory after the build; do not overwrite an existing file without checking its digest. `--old-asset-ttl` alone did not keep every previous chunk reachable during the 2026-11-14 deployment. This protects the specifically retained version, not arbitrarily old versions or a tab with a stale non-content-addressed loader.
