# JTD デコード監査（2026-11-10）

対象実装は `0697583`（`jtd-page-geometry`）。**現状は本文を正しく復元できていない。**
罫線の表示調整だけでは修復できない欠落を、元バイト列・PDF・独立した診断処理で確認した。
この監査では importer やブラウザー配信は変更せず、診断と再現可能な根拠を追加する。

**後続の修復:** 本資料は`0697583`時点の記録。指摘した本文復元・TLV解析等は
その後の[構造化インポート](jtd-structured-import.md)で修復し、さらに
[書体・文字送り・罫線](jtd-layout-compatibility.md)を改善した。
現在の作業仕様は[JTD形式メモ](jtd-format-notes.md)を参照。

## 1. 確認した本文欠落

ローカルの `03新旧（整備令）.jtd` と同名の一太郎生成 PDF を使用した。
原本は変更せず、本文、作者情報、原本ファイルをリポジトリに追加していない。
文字数の比較は Unicode NFKC 後に空白を除いたもの。文字の出現数と文字順は別に検査する。

| 測定対象 | 結果 |
| --- | --- |
| JTD の `DocumentText` | 46,064 bytes、256 bytes × 177 blocks |
| ディレクトリから再構成した sub-stream 0 | `TextV.01`、45,059 bytes |
| 宣言された本文 | 21,322 UTF-16 units（制御・レコード込み） |
| 書式領域の独立した走査 | 105 change events、カバー範囲はちょうど21,322 units |
| レコード境界に従って抽出した本文 | **4,105文字** |
| 元PDF | 9ページ。本文サイズ11.16ptの文字は4,105文字で、JTDと文字の種類・出現数が完全一致。残り8文字は各ページ下部のページ番号1〜8 |
| 現実装から今回生成し直したDOCX | **3,609文字**、496文字不足・余分な文字0 |
| インライン終端直後の平文 | **25か所、496文字** |

`jtd.rs::extract` はインライン本文を読み終えた後、終端 `001e` の次から
次の `001c` を探す。5語の終端 `001e 0005 0000 0001 001f` の後に続く通常の本文を
取り込まない。欠落箇所の文字数が496文字に一致した。
完全な終端を持つ合成データ `甲`（インライン）+ `乙丙`（通常本文）でも、
既存テストに `IBIS_JTD_EXPECT=甲乙丙` を与えると失敗する。

EZPZ CLI のJSON・text出力には77個のU+0008が余分に含まれた。それを明示的に除くと、
独立診断の本文と**文字順も完全一致**した。外部出力そのものを正解にはしていない。
PDFの抽出順は本文ストリーム順と異なるため、PDFとの全文の文字順一致は主張しない。

別の実文書 `a5.jtd` でも、独立診断の本文38,564文字に対し現DOCXは17,156文字。
文字出現数では不足21,411・余分3であった。インライン後の読み飛ばしだけでなく、
断片境界などもあるため、この差全体を単一原因と断定しない。

## 2. ブロック格納を解読せず物理順に走査している

`extract` は `SsmgV.01` の全領域をUTF-16BEに変換して走査している。
実際には、ヘッダー、固定長ブロック、sub-stream のディレクトリからなる格納形式である。
本文の後に書式データがあり、末尾に索引がある。これらは本文ではない。
`a5.jtd` は4断片、`03_230301_新旧.jtd` は40断片を並べる `QLSTV.01` であった。

反証実験として、対象JTDのローカルコピー上で物理ブロック8と9を交換し、
ディレクトリの参照も交換した。再構成後の本文21,322 unitsは**完全に同一**。
一方、現実装のDOCX本文は3,609文字から3,586文字に減り、文字順も変わった。
格納位置だけに依存して本文が変わることを確認した。
これはディレクトリ仮説に基づく変形試験であり、一太郎での再保存・再オープン試験ではない。

今回の診断で読めたローカル `.jtd` 22件では、全sub-stream内のブロックは連続していた。
そのため、この実験を「元の対象文書も非連続だった」と解釈してはいけない。
対象文書で観測された496文字欠落は、上記のインライン処理が直接の原因である。

## 3. 罫線ヘッダーは固定位置ではない

対象のclass `0010`ヘッダー151個は、先頭0、`tag/count/values`の列、`ffff 0000`の
終端として全件を境界ぴったりに読めた。`008f` はその中のTLV項目である。

| 項目 | 実データ | 現実装 |
| --- | --- | --- |
| `008f`罫線ヘッダー | 130個 | 固定位置・全長条件に合う128個だけ認識 |
| 認識しない2個 | 本文unit offset 3,891 / 4,117。前に`002a`項目がある | `RowStart`を生成しない |
| 罫線項目 | 708個。全130行で距離の合計と宣言幅が一致 | 未認識行を含めて完全には扱えない |
| `b`に縦罫線classが立つ項目 | 54個 | `centre + a + 1`の付加的な縦罫線を生成する処理がない |
| 線種 | 本文unitに対応する書式イベントにも格納されるという公開分析 | 書式イベントを読まず、一律の細い黒実線 |

ローカル22件では `008f` 6,092個の全項目で距離の合計が宣言幅と一致し、
うち123個が現実装の固定位置条件に合わなかった。文法の整合性を示す証拠にはなるが、
全線分の実描画との一致、未知バージョンへの適用を保証するものではない。

## 4. Word表への変換に、未検証の形状補完がある

実装は行内の区画宣言を一度Word表に変換し、狭い空白区画を削除し、隙間に区画を補い、
区画端の中点を列境界にして、隣接表のグリッドを統合する。これらは原形式の復号結果ではなく
推定である。特に`±4`での補完、幅2以下の区画削除、幅6以下の外周除去は普遍的な規則ではない。

対象では元の表示行130に対しDOCXは32表・121表行。表示行とWordの論理表行は同じ概念で
はないので、単純な行数一致を合格条件にはできない。しかし現在はsource行からmodelへの
対応を保持しておらず、どの行を統合・脱落させたか説明できない。
元PDFの2・5ページでは大きな新旧対照の領域と細い見出し領域が連続している。
出力表の数やセル数だけでは、この配置を再現した証拠にならない。

また対象JTDは `1006` で既定文字サイズ393（1/100mm、約11.14pt）、
`100b` で134半角桁（67字）を指定している。現DOCXは既定10.5ptで、明示的な文字サイズ・
字間指定を出していない。用紙A4・余白・26行を読めても、文字送りは一致しない。
既存のWord組版は文字・ルビ・書字方向・ページ・罫線を表示する機構として使えるが、
誤った復号や推定した表の形は組版側では修正できない。

## 5. 参照仕様自体にも未確定部分がある

- EZPZ §2.2の記述に加え、手元のpiece-list rootには末尾4 bytesがある。
  `a5`では0、大きい新旧対照では39。今回の診断は値を保持し、意味を推測しない。
- EZPZ §5は`ff`を終了とする記述だが、対象とhello文書等の書式領域はrun命令の
  直後にsub-stream境界で終わる。本文unit数との被覆一致を独立に検査する必要がある。
- 22文書すべての本文領域は文法に従って走査できたが、書式は1文書の1断片に
  未対応の末尾形状があり、診断結果にエラーとして残す。
- Tika RFCの改ページ等の記述には節間・他資料との不一致がある。
  旧readerの内部形式の観察を、そのまま現代のJTDのディスク形式とみなさない。

## 6. テストの問題と修復順序

現状の `local_sample_can_be_read` は、同じ `extract` による本文と、そこから作った
モデル・DOCXを比較する。原本でなく自分自身を基準にしていた。
今回も原本と並べ替えコピーの**両方で成功**し、欠落を検知しなかった。
複数の従来合成テストも、実際のブロックストアを持たない`SsmgV.01 + units`形式や
不完全なインライン終端を使用している。既存テストの成功は形式適合の証拠にできない。

修復は次の順序とするのが妥当である。

1. ブロックディレクトリとpiece-listを復元し、本文・書式・未使用領域を明確に分離する。
2. 通常・インラインレコードを終端まで検証する。後続本文を失わず、未知要素を位置付きで保持する。
3. ヘッダーのTLVと、unit位置に対応する書式状態を読む。確度の異なる仮説を区別する。
4. 表への推定変換の前に、表示行・文字グリッド・線分と原本のoffsetを持つ中間表現を作る。
5. PDFの文字、線分座標、改ページを独立した期待値として照合した後、Wordモデルへ変換する。

最低条件は、対象本文4,105文字の順序付き保持、ブロック配置の変更に対する不変性、
全130罫線行の対応追跡、片側・半分の罫線と空行の保存、文字送りの校正である。
文字出現数の一致、DOCXの再読込、Webビルドだけでは見た目の合格にしない。

## 再現

必要なPythonパッケージは`olefile`、PDF照合時は`PyMuPDF`。
診断は本文を標準出力せず、整数・hash・offsetのみを出す。

```sh
python3 -m unittest discover -s scripts -p test_audit_jtd.py -v

IBIS_JTD_SAMPLE='/path/to/sample.jtd' \
IBIS_JTD_DOCX_OUT='/tmp/jtd-audit-current.docx' \
cargo test -p ibis-pptx --lib jtd::tests::local_sample_can_be_read -- --ignored --exact

python3 scripts/audit-jtd.py '/path/to/sample.jtd' \
  --pdf '/path/to/sample.pdf' --docx '/tmp/jtd-audit-current.docx'
```

外部比較JSONがあれば`--external-json /path/to/ezpz.json`を指定できる。
原本なしでも、次のコマンドでメタデータを含めて完全に合成したCFB/JTDを生成できる。
`inline.jtd`はインライン後続本文の欠落、`ordered.jtd`と`reordered.jtd`は
同じ本文に対する物理配置依存を検証する。256-byteブロックを使い、CFBの通常セクターに
格納するため未使用ブロックを含む。一太郎での受理を保証するfixtureではない。

```sh
python3 scripts/test_audit_jtd.py --write-probes /tmp/jtd-probes

# 現実装ではFAILEDとなる。本文は「甲乙丙」だがDOCXは「甲」のみ。
IBIS_JTD_SAMPLE=/tmp/jtd-probes/inline.jtd IBIS_JTD_EXPECT=甲乙丙 \
cargo test -p ibis-pptx --lib jtd::tests::local_sample_can_be_read -- --ignored --exact
```

同じ手順で`ordered`/`reordered`をDOCX出力して診断すると、独立診断は両方140文字、
現importerはそれぞれ140/112文字になる。既存テストは両方で成功する。
追加した診断の合成テスト8件は成功。現importerの最小インライン反証は期待どおり失敗。
通常の`cargo test -p ibis-pptx ...`は無関係なXLSXテスト用TSV不足でコンパイルできないため、
上の`--lib`に絞って実行した。ブラウザー・Word実機・LibreOfficeの描画一致は検証していない。
