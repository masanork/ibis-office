# 構造化データのプレビュー

デスクトップ版の「開く」から、UTF-8 の JSON／XML、SD-JWT の
コンパクト形式、mdoc の単一文書（CBOR またはテキスト表現）を読み取れます。
項目名と値を並べ、元の位置をパスで表示します。文字列と数値を見分けられるよう、
JSON の文字列は引用符で囲み、数値は元の精度で表示します。
既存の法令 XML や FHIR の専用ビューが該当する場合は、そちらが優先されます。

プレビュー中は編集や保存を行いません。XML の DTD は読み込まず、
内容をリンクやスクリプトとして解釈しません。最大 1 MiB、1,000 項目、
32 段の階層までを対象とし、長い値は省略記号付きで表示します。

## 外部の表示定義でXMLを読む

デスクトップで `data.xml` と同じフォルダーに `data.view.json` を置くと、
XMLの要素を日本語名などで表示できます。定義の `root` にはルート要素の
名前と名前空間URI、および照合する属性を記述します。`entries` の配列順が
表示順になり、`group` は一致した要素ごとに明細を表示します。
定義を保存してXMLを開き直すと、その内容を反映します。

[e-Taxの生命保険料控除証明書の試用ファイル](../test/fixtures/structured-preview/etax)
には、国税庁の公開スキーマ TEG800-001 の VR 1.1 に沿った合成XMLと表示定義が
あります。証明書の署名欄には試験用の値を入れています。
[国税庁の公開仕様](https://www.e-tax.nta.go.jp/shiyo/ksk2/ksk2_shiyo-kojo3.htm)

### 複数のXMLで表示定義を共有する

デスクトップ版の **設定 → 一般 → 表示定義フォルダーを開く** を選び、
開いたフォルダーに共有する `*.view.json` をコピーしてからXMLを開き直します。
フォルダーがまだなければ、ボタンを押したときに作成します。
アプリのデータフォルダー内の配置は `ibisOffice/xml-views` です。macOSでは標準で
`~/Library/Application Support/ibisOffice/xml-views` です。
Windowsでは `%APPDATA%/ibisOffice/xml-views`、Linuxでは
`$XDG_DATA_HOME/ibisOffice/xml-views`（未設定なら `~/.local/share/ibisOffice/xml-views`）です。
`IBIS_DATA_DIR` を設定している場合は、その配下の `ibisOffice/xml-views` を使います。

先にXMLと同じ場所の個別定義を確認します。個別定義がなければ、共有定義の
ルート要素名と名前空間URIに加え、`root.attributes` のルート属性と
`root.elements` の要素値を照合します。共有定義には属性か要素値の条件が必要です。
両方を指定した場合はすべての条件が必要です。`root.elements` は `path` と
`value` の組を並べ、各パスにはルートからの子要素名を指定します。表示項目と同じ
名前空間の接頭辞が使えます。パスがテキストだけを持つ要素1件に一致し、
前後の空白を除いた値が `value` と完全に一致すると条件を満たします。
共有定義のファイル名は末尾が `.view.json` であれば任意です。
条件のない定義や読み取れない定義は共有選択から除外し、一致がなければ通常のXML表示になります。
複数の定義が一致すると、開く操作を止めて競合したファイル名を表示します。
エラー画面の **表示定義フォルダーを開く** から不要な定義を外してXMLを開き直すと、残った定義が適用されます。

試すには、[e-Taxの試用ファイル](../test/fixtures/structured-preview/etax)から
生命保険（TEG800）と地震保険（TEG810）の表示定義を共通フォルダーにコピーします。
合成XMLだけを別のフォルダーに移して開くと、どちらも同じ名前空間と版
（`VR="1.1"`）を使い、ルート要素に応じた表示になります。

[FDSN StationXML 1.2の試用ファイル](../test/fixtures/structured-preview/stationxml)でも、
共有定義をコピーして観測所の名前・座標・標高の表示を確認できます。

[気象庁防災情報XMLの表示定義](../test/fixtures/structured-preview/jma)では、ルート属性の代わりに
`Head` の `InfoKind` と `InfoKindVersion` の値を照合します。

## 連携CSVを定義に沿って確認する

自治体標準仕様の連携CSVと同じフォルダーに、`mrlgss` の
`describe <連携ID> --json` で書き出した定義を置きます。
たとえば `data.csv` に対しては `data.definition.json` と命名します。
デスクトップ版でCSVを開くと、列名と列順が一致した場合に値の検査を行います。
指摘を選ぶと、該当するレコードの項目と元の値を読み取り専用ビューで確認できます。

「指摘をXLSXで保存」では、検査したレコードから指摘ごとに1行を書き出します。
データ番号、宛名番号、項目名、元の値、指摘理由を収録し、画面に表示しきれない指摘も含めます。
宛名番号や元の値を文字列として保持し、該当する列がない場合は空欄になります。

対象は繰り返しのない必須項目、X・N・整数の型と桁数、および定義に含まれる
コード一覧です。画面には検査したレコード数と全レコード数を表示し、先頭20件の
指摘へ移動できます。

定義に条件付き必須の情報がある場合は、同じレコード内の参照列が指定値と一致する条件と、
参照列に値がある条件を検査します。先頭ゼロを維持し、引用符の有無を問わず空文字は
値なしとして扱います。参照列が無い、複数ある、繰り返しを含む、または条件を
定式化できない場合は「判定不能」に表示します。日付や、ファイルをまたぐ整合性は対象外です。
`mrlgss describe <連携ID> --row-schema` で同じ条件をJSON Schemaとして出力できます。

## JSONLを行スキーマで検査する

`mrlgss` の `node src/linkage-csv-cli.ts describe <連携ID> --row-schema` で出力する
JSON Schemaを、同じフォルダーの `data.jsonl` に対して `data.schema.json` として置きます。
デスクトップでJSONLを開くと、各物理行を独立したJSONオブジェクトとして検査します。
指摘を選ぶと該当行とフィールドを表示します。欠落したフィールドは名前と欠落理由を表示します。
壊れた行も行番号付きで記録し、後続の行の検査を続けます。

このプレビューは、生成されるDraft 2020-12の行スキーマに対応します。
利用するキーワードは `type`（object、string、null）、`properties`、`allOf`、
`if` / `then`、`required`、文字列の `enum` / `minLength` です。
評価できない条件を記した `$comment` も表示します。
プレビューは128 MiB以下のファイルを先頭100万行まで検査し、指摘は先頭20件を表示します。

## ネストしたJSONをスキーマで検査する

デスクトップで `data.json` と同じフォルダーに `data.schema.json` を置きます。
JSONLと同じ検査処理で、JSON文書全体を1件として確認します。指摘の位置はJSON Pointerで表示し、
選択すると該当するオブジェクトのフィールドや配列まで展開します。

たとえば `/team/contacts` の各要素に `items` で名前と主連絡先フラグを要求し、
`contains` で `primary` が `true` の要素を選び、`minContains` と `maxContains` を
ともに1にすると、主連絡先がちょうど1件か確認できます。
名前が空なら `/team/contacts/0/name`、件数が合わなければ `/team/contacts` に指摘します。

対応範囲は、前項のキーワードと、ネストした `properties`、`items`、
`contains` / `minContains` / `maxContains`、型 `array` / `boolean`、
文字列・真偽値・nullの `const` / `enum` です。未対応キーワードを含むスキーマは読み込み時にエラーを表示します。

### スキーマの値を編集して試す

デスクトップで `*.schema.json` を開き、ツリーでスカラー値を選択して「JSONの値を編集」を選びます。
数値、引用符付きの文字列、真偽値、nullを入力し、「反映」してから「スキーマを別名で保存」でコピーを保存します。
たとえば `maxContains` を `1` から `2` に変えると、条件を満たす配列の要素を2件まで許容できます。

元のデータのビューで「JSON Schemaを選択」から保存したコピーを開くと、そのデータを再検査できます。
既存のスカラー値が編集対象です。オブジェクトや配列の構造の変更は対象外です。

## 修了記録で試す

[test/fixtures/structured-preview](../test/fixtures/structured-preview) の
`training.json`、`training.xml`、`training.sd-jwt`、`training.mdoc`
を順に開いてください。全て架空の記録です。

- どのファイルにも研修名と修了日があります。
- JSON と XML では管理番号 `00123` も読めます。Wallet の提示サンプルには
  管理番号が開示されていません。提示だけから、元の資格情報に管理番号が
  存在するかは判断できません。
- 資格情報のプレビューが表示する照合件数は、ファイル内の開示データと
  ダイジェストとの一致数です。署名、発行元の信頼性、保有者や端末への
  結び付けを確認したという意味ではありません。

サンプルはテスト用の鍵で生成しています。再生成する場合は
`cargo run --locked -p ibis-formats --example structured_preview_samples -- <出力先>`
を実行してください。

## 次に確認すること

upstream への提案前に、Wallet の実装を知らない利用者にこの記録を開いてもらい、
「何を受け取ったか」「何が提示に含まれないか」「何が未検証か」が
表示だけで分かるか確認します。提案の中心は、構造化ファイルを文書編集や
外部サービスへの送信を伴わず閲覧できることです。

フォームへの事前入力は、確認画面で転記元の項目、転記先の欄、変更前後を
確認できる設計から始めます。まず名前付きセルを持つ Excel を対象にし、
その後に入力欄付き PDF と、利用者の同意を経た Wallet 連携を検討します。

## 進行役向けの短い試用

5〜10分を想定します。Walletの実装を知らない人に
[参加者用カード](../test/fixtures/structured-preview/pilot-participant-ja.txt)だけを
先に渡し、上のサンプル解説と下の判定表は見せません。ファイルは次の順に
一つずつ渡します。

1. `training.sd-jwt` または `training.mdoc`。まだJSONやXMLは渡しません。
2. `training.json` または `training.xml`。
3. [空の入構申請書](../test/fixtures/structured-preview/site-entry-form.xlsx)。
   最初の提示だけを転記元として考えてもらいます。

操作方法を聞かれたら、まずどこで迷ったかを記録します。答えや画面の意味は、
三つの課題が終わるまで説明しません。参加者ごとに、使用した形式、
各課題の所要時間（目安）、助けを求めた箇所、本人の言葉を匿名で記録します。

| 観察すること | 画面から読み取ってほしいこと |
|---|---|
| 提示だけで読める情報 | 「安全研修（サンプル）」「2026-04-01」。署名や発行元の信頼性は画面上では未確認 |
| 二つのファイルの違い | JSON／XMLには管理番号 `00123` があるが、提示には出ていない。提示だけでは元の資格に番号がないとは言えない |
| 申請書への転記 | 「受講した研修」「修了年月日」は提示から埋められる。「申請者氏名」「研修記録の管理番号」は追加確認が必要 |

日付や項目を見つけにくければ表示を改善します。違いの説明で迷うなら
比較表示を優先します。読み取りと比較ができ、転記だけが手間なら、
名前付きセルへの入力候補と変更前後のプレビューを試作します。

## Excel への事前入力を確認する

合成のWallet提示を元に、入構申請書の名前付きセルへの転記候補を
CLIまたはMCPで確認できます。次の例は、提示に含まれる研修名と修了日を
B5／B6への候補として表示します。氏名は手入力、提示にない管理番号は
「このファイルに含まれない」と判定します。

```sh
cargo build --locked -p ibis-mcp --example prefill_preview
target/debug/examples/prefill_preview \
  test/fixtures/structured-preview/site-entry-form.xlsx \
  test/fixtures/structured-preview/training.sd-jwt \
  test/fixtures/structured-preview/prefill-sd-jwt.json
```

MCPでは `app_open_document` の後に、`xlsx_preview_prefill` へ
`document_id`、`sheet`、`format`、`source`（ファイルの内容）、
`mappings`（転記元パスと転記先の名前）を渡します。元の値と候補を返す
読み取り専用ツールです。保護されたシート、数式、結合セル、非表示の
行・列は転記対象外とし、値がある欄は上書き候補から区別します。
資格情報の発行元の信頼性は `not_checked` と表示します。
この試作はExcelを対象としています。

### 選んだ候補を新しいXLSXに反映する

上のCLIコマンドの出力を `review.json` に保存し、値と転記先を確認します。
同じ3つの引数に `--apply`、確認結果、まだ存在しない出力先、
選んだ名前付きセルを追加します。

```sh
target/debug/examples/prefill_preview \
  test/fixtures/structured-preview/site-entry-form.xlsx \
  test/fixtures/structured-preview/training.sd-jwt \
  test/fixtures/structured-preview/prefill-sd-jwt.json \
  --apply review.json filled-entry-form.xlsx training_name completion_date
```

元のブックとソース、転記計画が確認時点と一致し、選択した候補がすべて
`ready` のときだけ出力します。文字列は `=` で始まっても文字として
扱います。反映できる型は文字列、真偽値、15桁以内の整数です。
署名付きブック、数式、スピル範囲、既存値のある欄は反映対象外です。

書き込み可能なMCPセッションでは同じ引数に `preview_id` と選択した
`targets` を添えて `xlsx_apply_prefill` を呼び出せます。反映は
取り消し可能な1ステップで、ファイル保存は別の操作です。

### デスクトップのExcel画面から確認する

入構申請書を開き、**書式 → フォームの入力候補を確認…** を選びます。
最初に `training.sd-jwt`、次に同じフォルダーの
`prefill-sd-jwt.json` を選んでください。

結果には申請書の項目名とセル、転記元、現在の値、候補の値が表示されます。
表示は開いているシートを対象とし、確認ダイアログではブックを変更しません。
対応表の `label` は表示用で、省略時には名前付きセルの名前が表示されます。
この画面はデスクトップの試作です。

### デスクトップの確認画面から別名で保存する

開いているファイルが編集可能な暗号化されていないXLSXなら、確認画面で
入力したい欄にチェックを付け、**選んだ欄を新しいXLSXに保存…** を選べます。
最初はどの欄にもチェックが入っていません。保存先には未使用の名前を選びます。
元のブックや転記元、対応表が変わっていた場合は、もう一度プレビューします。
出力は元のブックと別のファイルで、元のシートに変更を適用しません。
