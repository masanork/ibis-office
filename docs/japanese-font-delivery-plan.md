# 日本語フォントの提供と表示の整理

## 目的

IPAmj 明朝と追加文字行政事務標準明朝を、文書内の文字と書体指定に応じて扱う。通常の Web 利用では、表示できる文字のために起動時から大きなフォント全体のダウンロードを要求しない。既存の文書や保存された書体指定を勝手に変えない。

## 文字の検出と表示

- 文書全体から必要な文字・書体と、基底文字と異体字セレクタから成る IVS を収集する。本文以外の表、ヘッダー、脚注、表示外のシート・スライドも対象とする。編集で後から挿入・変更した部分も再評価する。
- JIS X 0213 の範囲外、IVS、私用領域は調査の手掛かりとする。JIS の対応判定は版と対応表を明示し、Unicode の単純な符号範囲では代用しない。私用領域は意味が文書・利用元に依存するため、すべてを行政事務標準文字として扱わない。
- 基底文字の cmap、IVS の cmap 14、必要に応じたシェーピングを確認し、基底文字が表示できるだけで指定された異体字が表示できると判断しない。未収録、字形代替、フォント取得失敗を区別する。
- Web では利用可能なローカル書体を調べ、不足分を許可された WebFont サービスから必要に応じて取得し、描画に反映する。字形を取得できない場合やオフライン用フォントを利用者が明示的に求めた場合に、必要な導入・代替方法を提示する。起動時の一律のダウンロード案内は見直す。
- WebFont には文書から収集した文字が送られる。配信先、送信範囲、キャッシュ、有効期限を説明し、機微な文書やオフラインを重視する利用者が選択できるようにする。フォントのライセンス・表記・出典と、ローカル保存時の整合性検証を維持する。

## フォントセット

利用者が「IPAmj 明朝＋追加文字行政事務標準明朝」を一つの論理的な書体セットとして選べるようにする。IPAmj を基本とし、対象の追加文字を追加明朝で補う。ゴシックなど別の指定や明示されたフォントを尊重し、補完の順序と対象文字の同定方法を明記する。

論理セットは複数のフォントファイルの選択規則であり、物理的な統合フォントを意味しない。DOCX 等には互換性のある書体指定を保存し、ほかのアプリでの欠字・代替を検証する。字形の合成や対応表変換は、ライセンスと利用条件を確認し、外字に誤った意味を付けない。

## 検証と段階

1. WebFont とインストール済み書体の能力・取得元・失敗時の状態を可視化し、IVS と私用文字の欠落検出を修正する。
2. 論理フォントセットの選択とレンダリングを導入し、既存文書の書体指定と保存互換性を確認する。
3. Web の自動ダウンロード案内を字形不足・利用者の選択に基づく形へ変更する。デスクトップは別のインストール方針として扱う。
4. 起動の転送、展開、整合性検証、Wasm のコンパイル、フォント取得、文書の初回表示を分けて計測し、単一・分割の性能を条件別に比較する。

合成 DOCX を起点に通常文字、JIS の境界、IVS あり／なし、基底字形のみ対応、行政事務標準文字と無関係な私用文字、追加文字の混在を検証する。編集挿入、再描画、保存・再読込、他アプリ、PDF と、可能なら XLSX・PPTX も確認する。通信失敗・オフライン・キャッシュ更新・再起動と実ブラウザ／実機を含める。

上流の関連議論: [行政事務標準文字と IVS](https://github.com/ibisjp/ibis-office/issues/158)、[Web での字形取得](https://github.com/ibisjp/ibis-office/issues/157)、[Wasm の配信分割](https://github.com/ibisjp/ibis-office/issues/152)。

## Wasm 配信の予備測定（2026-11-14）

本番に公開した release の同一 Wasm は 76,065,556 バイト、SHA-256 は `49b838c681694e9407bc96f8188e80c726bb0a83269b2ead4f44429c95c1deef`。そのままでは Cloudflare Workers Static Assets の単一ファイル上限 25 MiB を超える。転送圧縮後のサイズと、アップロードする個々のアセットのサイズは別に扱う。

gzip レベル 6 で事前圧縮すると、単一ファイルは 19,718,283 バイト（約 18.8 MiB）となり、データ自体は上限に収まる。4個を独立圧縮した場合の合計は 19,717,955 バイト。同じ Wasm をローカル HTTP サーバーから送り、Chrome の DevTools で下り 5,000,000 B/s・遅延 40 ms、キャッシュ無効にした予備試験では、各3回の中央値は次のとおり。時間は取得開始から Wasm のコンパイル完了までで、アプリ全体や文書表示までの時間ではない。

| 方法 | 整合性検証 | 中央値 |
| --- | --- | ---: |
| gzip を展開する単一配信 | 全体 SHA-256 を検証後にコンパイル | 4,083 ms |
| gzip を展開する4並列配信 | 各部と全体の SHA-256 を検証後にコンパイル | 4,172 ms |
| gzip を展開する単一配信 | 明示的なハッシュ検証なし、streaming compile | 3,998 ms |

単一の streaming 行は検証条件が異なる。ローカルの HTTP/1.x、固定した回線条件、同一端末、少数回の観測であり、Cloudflare の実配信や実機における優劣は分からない。これらの差だけで方式を決めない。単一 gzip の実配信には、保存済み圧縮データをブラウザが正しく展開し Wasm として扱うためのヘッダーまたは展開処理が必要で、Cloudflare の転送圧縮と混同しない。

次は同一ビルド・同等の SHA-256 検証条件で、分割版と圧縮済み単一版を別の検証先に用意する。初回／再訪、モバイル回線、複数ブラウザを分け、転送量と TTFB、展開・検証、コンパイル、最大メモリ、文書の初回表示を測る。単一版の streaming compile と整合性確認の両立、キャッシュ更新、ブラウザ対応、配信時の二重圧縮を検証する。`wasm-opt` は今回の公開ビルドに適用されていないため、その効果も別途測る。

## Cloudflare 配信の比較（2026-11-14）

本番とは別の公開検証 Worker に、同じ Wasm の事前圧縮アセットだけを配置して比較した。単一版を本番アプリの計測用ブラウザにのみ差し替え、Wasm 全体の SHA-256 を検証してから起動した。本番の通常の読み込みコード・配信設定は変更していない。検証用 Worker は測定後に削除する。

| 方式 | 圧縮済みサイズ | 起動時間の中央値 |
| --- | ---: | ---: |
| 本番の Brotli 4分割 | 約 17,432,000 バイト | 4,195 ms |
| 単一 Brotli（事前圧縮レベル5） | 15,031,574 バイト | 3,701 ms |
| 単一 Brotli・コンパイルと取得を並行 | 15,031,574 バイト | 3,674 ms |

各3回、キャッシュ無効の Chrome、390×844 のタッチ画面エミュレーション、下り 5,000,000 B/s・遅延 40 ms。空のアプリを開き、読み込み表示が消えるまでの時間で、文書の描画完了ではない。フォント設定ダイアログは抑止している。通常版の測定値は 4,330 / 4,179 / 4,195 ms、単一版は 3,815 / 3,690 / 3,701 ms、コンパイル並行版は 3,729 / 3,674 / 3,674 ms。コンパイル並行版も、検証に成功するまではアプリにモジュールを渡さない。分割版は各チャンクと全体、単一版は全体を検証する。

別の保存プロファイルに 1 GiB のキャッシュ枠を指定した確認では、単一・分割ともに再訪時の Wasm 転送がゼロになった。一方、Chrome の一時プロファイルでは単一版が再取得され、分割版は一部のみキャッシュされた。ブラウザ・キャッシュ容量による差が大きいため、後者だけを一般化しない。

この測定はデスクトップ Chrome、同一端末、少数回であり、実機・Safari・初回の文書表示・ピークメモリは未確認。事前圧縮版を採用する場合は、非対応クライアントへの応答、二重圧縮、正しい MIME・Content-Encoding、キャッシュの版混在、検証失敗時の挙動、ストリーム複製によるメモリ使用量を確認し、十分な証拠が揃うまで分割版に戻せるようにする。再現用の検証アセット生成と起動計測は `scripts/wasm-benchmark/` に置く。
