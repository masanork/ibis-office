# ibisOffice Markdown・YAML 入出力仕様

本書は、ibisOffice が Markdown 原稿をどう識別し、編集可能な文書に変換し、再び書き出すかを定義する。個別の構文、値、作例は [Markdown 構文リファレンス](markdown-reference-ja.md)、参照した外部仕様と適合範囲は [互換性一覧](markdown-compatibility-ja.md) に置く。

## 入力と処理経路

原稿は UTF-8 のテキストとする。共通の本文構文は見出し、段落、リスト、引用、リンク、画像、強調、コード、水平線を含み、GFM 由来のパイプ表、タスクリスト、取り消し線と脚注、アラートを加える。対応する MyST・Obsidian 構文は同じ本文に混在できる。文書全体に方言の指定は要らない。

通常の Markdown オープン時に認識される形式指定と処理経路は次のとおり。CLI の明示的な変換先指定はそのコマンドの経路に従う。競合する形式指定は原稿に併記しない。

| 指定 | 処理経路 |
| --- | --- |
| `x-ibis-format: lawtext` | Lawtext の法令構造を読む。編集用 Markdown と法令 XML の関係は後述する。 |
| `x-ibis-format: presentation` | スライドとして開く。プレゼンテーション指定の別名は `slides`、`pptx`。 |
| `x-ibis-format: document` | 通常の文書として開く。OKF の `type` が旧形式名と重なる場合にも使用する。 |
| 明示キーがなく `marp: true`、`slides: true`、旧来の `type: presentation`、`type: slides`、`type: pptx` のいずれか | スライドとして開く。 |
| 旧来の `type: lawtext` | Lawtext として読む。 |
| 上記以外 | 通常の文書として開く。CLI の表変換では XLSX も指定できる。 |

通常文書は本文を Word 相当の編集モデルへ写す。スライドは区切りごとに PowerPoint 相当の編集モデルへ写す。拡張から文書・スライドモデルへの変換は、共通の段落、画像、リンク、グラフなどを用いる。Markdown への書き出しは編集モデルにある情報から対応記法を生成する。

## YAML フロントマター

フロントマターは、先頭の単独行 `---` から次の終端の `---` までとする。LF と CRLF を受け付ける。一般の文書・スライドのフロントマターは終端の `...` も受け付ける。OKF の概念認識にはファイル先頭の開始行と `---` の終端が必要。本文中の `---` は、対応する文書構文の水平線、またはスライド経路の区切りとして処理する。

| 利用箇所 | 認識する値と扱い |
| --- | --- |
| 形式選択 | トップレベルの `x-ibis-format` を旧形式指定より優先する。ここに示したキーは単純な一行のキーと値で指定する。 |
| 通常文書の設定 | 文書情報、ページ、書体、段落、表示、編集に対応する定義済みキーを適用する。キー、別名、値は [文書の front matter](markdown-reference-ja.md#文書の-front-matter) を参照。 |
| プレゼンテーション | `size` は `16:9` または `4:3`。Marp の `headingDivider` は 1〜6 の整数か、その範囲のレベルを並べた配列。整数 N はレベル 1 から N まで、配列は指定レベルだけが区切りになる。フロントマターの YAML 配列はフロー形式とブロック形式を受け付ける。 |
| OKF のメタデータ | YAML マッピングを構造として読む。`type` は空白だけではない文字列。`title` と `description` は文字列。`tags` は文字列の列を使い、読み取りでは単一の文字列も受け付ける。 |

標準 YAML で記述できる任意の構造が、文書設定のすべてのキーに使えるわけではない。公開原稿では同名キーの重複を避け、文字列として扱う必要のある数値や真偽値に似た値を引用符で囲む。OKF の既存 YAML は Word のカスタムプロパティに保持する。編集反映の条件は後述する。

## 本文の拡張と競合回避

| 構文の出所 | 入力と書き出し |
| --- | --- |
| MyST | 見出しの直前の `(label)=`、対応する五種の単一段落 admonition、単一段落のキャプションを持つ `{figure}`。ラベル付き数式と、表示名を指定した `{ref}` による一意な同一文書内リンクを取り込む。図、数式、admonition はコードフェンスまたはコロンフェンスで囲める。図のラベル・代替テキスト・固定寸法・配置を対応する編集モデルに変換する。書き出しはブックマーク、アラート、画像、キャプション段落の記法を使う。 |
| Obsidian | `[[#見出し|表示名]]`、`[[ファイル#見出し|表示名]]`、対応する基本 callout、原稿のディレクトリー内にある画像への `![[path.png]]`。画像は通常の Markdown 画像として書き出す。同じ文書へのリンクは通常のアンカー記法で書き出し、別ファイルへのリンクは Wiki 記法で保持する。 |
| Marp | 区切り、指定した見出し、標準サイズと発表者ノートを PPTX に移す。本文のコメントで全体のサイズ・見出し区切りを上書きできる。`paginate` と `_paginate` で表示するページ番号をスライド右下に編集可能なテキストとして配置する。テーマの CSS と背景は対象外。 |
| Mermaid・chart | 対応するフェンスの内容を図または編集可能な Office グラフへ変換する。保持した Mermaid ソースを再出力できる場合がある。図種、要素、代替表示は [Mermaid](markdown-reference-ja.md#mermaid) を参照。 |
| Office Open Markdown | ブックマーク、配置、組版、セクション、フィールド、文献引用、変更履歴、セル結合などを Office の要素に対応させる。目次には `::: toc`、参考文献には `::: bibliography` を使う。旧原稿の `[[toc]]` と `[[bibliography]]` 系は書き換えが必要。 |

コードフェンス内では対応する言語名・ディレクティブだけが拡張を有効にする。一般のコードフェンスの本文はコードとして扱う。MyST からの変換は Word で表現できるラベルや内容に限定する。MyST のプロジェクト横断参照、引用、自動参照番号、および Obsidian のノート埋め込み、ブロック参照、折りたたみは対象外。

## OKF バンドルとローカルフォルダー

フォルダーを作業範囲として開く。可視の `.md` に上記の `type` がある場合は OKF の知識項目として認識する。予約ファイル `index.md` と `log.md` は通常のファイルとして開ける。メタデータの探索はファイルあたり 64 KiB までとする。

フォルダーペインと Assistant の `folder_list` は同じフィルターを使う。`type:Metric` は型の部分一致、`tag:finance` は個別タグの完全一致で、いずれも大文字と小文字を区別しない。単一値 `tags: "finance, ops"` は一つのタグなので、`tag:finance, ops` で一致する。`tags: [finance, ops]` には `tag:finance` と `tag:ops` がそれぞれ一致する。形式が不正なタグ値は検索対象に含めない。

通常の相対リンクは参照元のディレクトリー、先頭が `/` のリンクは開いたフォルダーを基準にする。Wiki リンクは作業範囲内のパスまたは一意な名前で引く。デスクトップで Git の過去コミットを開いているときは、リンク先もそのコミットから読む。通常ファイルの本文索引はフォルダーのオープン・再読み込み時に再構築し、元ファイルを変更しない。

### 信頼状態と鮮度

`verified` は `by` と `at` を持つマッピング一件、またはその配列を受け付ける。日時は RFC 3339 とし、日付だけの場合は UTC の午前零時を表す。`generated.at` と同時または以後の検証を現在の検証とする。`generated` がなければ有効な検証をすべて現在の検証とする。生成日時が不正な場合は未検証とし、生成日時の問題を示す。

現在の検証に `human:<id>` があれば「人による確認済み」、その他の検証だけなら「機械確認済み」、現在の検証がなければ「未検証」とする。表示する根拠は、その階層に該当する最新の検証者と日時。`stale_after` に達すると「要再確認」とし、期限がなければ「再確認期限なし」、値が不正ならその旨を示す。信頼状態と鮮度は独立して表示する。

デスクトップのフォルダーペインには、フォルダーのオープン・再読み込み時に読み取った検証情報を表示する。Assistant の `folder_read` は、読み取った原稿の `okf_review` に判定と根拠を返す。これらの操作は YAML を書き換えない。バンドルのパッケージングは別機能とする。

### バンドルの読み取り診断

開いたフォルダーで Assistant の `folder_diagnose_okf` を使うと、YAMLマッピングの読み取り、予約ファイルのフロントマター、型・タグ・日時、メタデータ内とMarkdown本文のローカル参照先を診断できる。本文は通常リンクと定義済みの参照形式リンクを点検し、参照を書いた行番号を返す。コードブロック、インラインコード、Wikiリンク、画像の埋め込みは本文リンク診断の対象外。参照先が見つからない場合は確認用の指摘として返し、文書は引き続き利用できる。外部URLは取得しない。

一回の診断は最大32件のMarkdownファイルを確認し、`next_offset` で続きを取得できる。フォルダー一覧の制限、読み取り失敗、指摘の件数制限に達した場合は `partial` を返す。本文は各ファイルの先頭512 KiBまでを確認し、上限を超えたファイルがある場合も `partial` を返す。リンク先がMarkdown文書の場合、明示ブックマークと見出しIDをデスクトップの移動時と同じ規則で確認する。ファイルの欠落と見出しの欠落は別の指摘を返す。1回の診断では最大32件の参照先を索引化し、上限や読み取りの制限で判定できない場合は `partial` を返す。予約ファイルの本文構造は別の診断とする。

## ラウンドトリップの契約

| 経路 | 保証の範囲 |
| --- | --- |
| Markdown → DOCX → Markdown | 対応する本文要素を編集モデルへ写して再生成する。空白、書式記号、方言の構文、外部レンダラーの見た目は保持の対象外。 |
| OKF → DOCX → Markdown | 保存した YAML のコメント、順序、未知キーを維持する。Office で変更したタイトル・説明・キーワードは、安全に対応を確認できる `title`、`description`、`tags` だけ書き換える。カンマを含む既存タグや複数行の値など曖昧な編集は原稿側に残し、対象キーを診断に含める。 |
| Marp → PPTX → Markdown | スライドと対応要素、発表者ノートを再生成する。ページ番号は位置付きテキストとして保持し、自動で再採番するフィールドにはしない。元の Marp の設定や区切り記法をそのまま復元する機能は対象外。 |
| Markdown 表 → XLSX → Markdown | ワークシートの表、対応する数式とシート名を表記できる。使用できる数式と出力例は [XLSX の数式とシート間参照](markdown-reference-ja.md#xlsx-の数式とシート間参照) を参照。 |
| 法令 XML ↔ Lawtext・編集用 Markdown | 法令 XML を原本にする。元 XML がある場合は、対応先と変更内容が確定した編集だけ原本に反映する。曖昧・未対応の編集は診断して保留する。法令文書の書き出し範囲は [法令標準XML と Lawtext](markdown-reference-ja.md#法令標準xml-と-lawtext) を参照。 |

この仕様は変換経路ごとの保持範囲を定める。デスクトップのフォルダー・Git 操作と、共通変換ライブラリーの構文対応は別の入口から検証する。公開 Web 版での対応は、利用できるファイル・フォルダー操作に従う。

## 回帰確認

- `cargo test -p ibis-formats --lib markdown::tests` で、正規化・再出力を含む Markdown と Office の変換を確認する。
- `cargo test -p ibis-formats --lib okf::tests` で、概念文書とパスの規則を確認する。
- `cargo test -p ibis-office-shell --lib folder_context::tests` で、フォルダーの絞り込み、参照、本文索引を確認する。

新しい方言構文は、既存記法との競合、通常の入出力での再生成、未対応入力の扱いを記録する。各外部仕様への適合範囲は [互換性一覧](markdown-compatibility-ja.md) を更新する。
